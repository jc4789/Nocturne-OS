# 作業の模型

## なぜ

長い作業で筋を失うのは、判断の材料が、決める瞬間に目の前に無いから。圧縮の要約は直前の細かい作業を一番詳しく残し、ユーザーの前の言葉、自分で覆した説明、別のファイルで決まった約束を落とす。本人が書く模型も本人の今の枠を写すので、枠と一緒にずれる。

- 2026-10-25 の 16 時間の会話では、ユーザーが伝えた観測（ブラウザーの worker 一本しか CPU を使わない、全体で 60〜65% を越えない）が模型の二回目の書き換えで消え、自分の計測で覆した説明が十四時間後に一番へ戻った。
- 2026-10-27 の 20 時間の会話では、31 回の圧縮の間、物差し（落ちるコマ、fps）を一度も測らずに編集を重ね、ユーザーの「止まって報告しろ」が四回続いた。
- 2026-10-28〜29 の会話では、フックが「測った」と数えた命令の大半が、媒体を写して窓なしの QEMU で動く試験の道具と、`build/qa/hikaku/` の記録フォルダーだった（10-28 の記録では measure 399 件のうち 251 件が hikaku のフォルダー）。測る道具を増やすほど、本物（媒体を窓付きで見る）から離れた。ユーザーは build/ を消し、媒体は一つ、窓なしは禁止と言った（同じ日の夕方に、写し一つと QEMU 二台までに緩めた。何台も起こしてページングに落ちたことが元の禁止の理由）。
- 2026-10-29 の別の回では、七つのサイトを撮って見比べ、違いを K57〜K63 と番号で並べて終えた。直した行は無い。測る・比べる・確かめ直す回は、欠陥を一つも直さない。欠陥はコードと仕様を読んで直す。

だから作業場を分け、書く人を分ける。フックは見せる。止めるのは、日本語の無い返事と、下の「止める命令」だけ。

| | 書く人 | 置き場所 | 目の前に来る時 |
|---|---|---|---|
| 模型 | 本人 | `.claude/mokei/<作業場>.md` | 圧縮・再開の後（フックが入れる）、自分で開いた時 |
| 会話の記録 | フック（事象から） | `.claude/mokei/<作業場>.jsonl` | 圧縮・再開の後、節目の促し |
| コードの覚え書き | 誰でも | `.claude/oboegaki.md` | そのファイルを読む・書く時 |
| コードのつながり | codegraph | `.codegraph/`（手元だけ） | 編集の直後、自分で引いた時 |

作業場の鍵は会話の識別子で、デスクトップのアプリでは再開しても同じ作業場が続く。置き場所は会話の始まりにフックが知らせる。

## 模型：今、頭に置く判断

形は自由。今の作業に要るものだけを書く。欄を埋めることは目的ではない。

- 目的：ユーザーの言葉のまま。言い換えると目的がずれる。
- 物差し：目的が叶ったときにユーザーが見て分かるもの（fps、落ちるコマ、実時間、画面）と、その今の値、前の回の値（組み直す前に取ったもの、または前の写しの媒体で取ったもの。無ければ「無い」）、取った条件。物差しは窓付きの QEMU を見て、ログを読んで取る。対象を絞った WPT の通った数は添える値で、物差しの代わりではない。
- 今の一番の説明（二番手があれば）、それぞれ何を見たら覆るか、何で確かめたか（その版のログ・画面・計測、または推測）。
- 原因のありか：我々のコードから順に。なぜそこか。
- 境界の設計なら、持ち主と境界。
- 次の一手：どの説明とどの説明を分けるか。

読み返せる長さに保つ。自由に書き換えてよい。フックがすべての版を記録に残すので、消した説明も後から辿れる。済んだ作業の一覧や事実の写しは要らない。起きたことは記録と git にある。説明を「説明」を含む見出しの下に置くと、その一行目が版の流れとして圧縮の後に並ぶ。

## 会話の記録：フックが書くもの

本人は書かない。`.claude/hooks/mokei.py` が一行一事象の JSON で残す：ユーザーの発言（原文。ハーネスの通知やサブエージェントの報告は数えない）、模型の版、編集したファイル、計測（serial.log を読んだ・撮った・QEMU を起こしたシェルの命令）、止めた命令、圧縮、自分の返事の頭、促し。

圧縮・再開の後に、フックが次を一度に入れる：

- 頭の一行：圧縮の回数、ユーザーの最後の発言からの時間、最後に測ってからの時間とその間の編集の数、最後の編集から測った数、説明の入れ替わりの回数。
- ユーザーの原文（最初のものと最近のもの。短い訂正はそのまま、落ちた分は一行の見出し）。
- 模型の版の流れ、編集の流れ（時間帯ごと）、最近の報告の頭、この会話の間のコミットと未コミットの変更。

要約をそのまま読むと、直前の作業へ戻りたくなる。記録は、自分の手間がどこへ行ったかを外から見せる。ユーザーの言葉と、版の流れ・編集の流れを並べて、同じ方向を向いているかを見る。向いていなければ、なぜそうなったかが今の説明の一番になる。「前から」「別件」と書きたくなったら、その判断がいつ何を根拠に模型へ入ったかを版で確かめる（`grep` で探せる）。

## 節目の促し

- ユーザーのいない時間が 2 時間ごとに一度、フックが節目を知らせる：何を測ったか・何が動いたか・次に何をするかの短い報告を書く、物差しが動かないなら同じ方向の次の一手へ進まない、自分が起動したもの（QEMU・ビルド・サブエージェント）を確かめる。
- 模型を書いてから編集が 40 件たまるごとに、模型を今に合わせるよう促す。
- 最後の編集から測る命令（ログを読む・撮る・QEMU を起こす）が 12 件たまるごとに、読んで直す側へ戻るよう促す。測る回は欠陥を直さない。
- 促しは一度ずつ。応じなくても止まらないが、記録に残る。

## 止める命令

フックは、シェルの命令が次に当たれば実行の前に止め、理由を返す（2026-10-29 ユーザーの指示）。止められたら、迂回せず、やり方を変える（`nocturne-project` スキル）。

- QEMU を `-display none`・`-nographic` で起こす。QEMU は窓付き。ユーザーはその窓を見ている。
- 三台目の QEMU を起こす命令（手で起こすものも、`wpt.py`・`test.py` が起こすものも）。二台まで。以前は何台も起こして RAM が尽き、ページングに落ちて速さの値が歪んだ。
- `scripts/wpt.py`・`test.py` を、窓なしの印（`-display none`・`CREATE_NO_WINDOW`）がスクリプトに残る間に走らせる。直せば通る。`platform_qa.py`・`qtest.py` は常に。
- `nocturne.img` の写しで三つ目の媒体になる命令（cp・copy・Copy-Item・robocopy・`qemu-img convert`、道具の写しも）。媒体は二つまで。
- `build/qa`・`build/nocturne-platform` に触れる命令（grep・ls など読むだけのものは除く）。build には今のビルドの出力と試験の道具の出力（`build/wpt/`）だけ。画像とログは会話の作業場（scratchpad）へ。
- 目標の無い `scripts/build.py`。既定の `all` は vhd・vhdx・iso まで作る。確かめは `qemu-image`、Hyper-V へ渡すときだけ `all` と書く。

## 返事の言葉

Stop のフックが最後の返事を見て、日本語がほとんど無ければ一度だけ書き直させる（識別子・パス・コマンドはそのまま）。ユーザーに見える文はすべて日本語。

## コードの覚え書き：次に触る人が知らないと困ること

コードを読んでも分からないことを苦労して知ったときに書く。ファイルをまたぐ暗黙の約束（ある関数の返り値の単位を、別のファイルの呼ぶ側が前提にしている、など）、落とし穴と確かめ方（この経路は QEMU では通らない、この道具は失敗しても成功を返す、など）、文書の古い箇所。一か所で完結する約束はその場所の注釈に書く。覚え書きは、触れる場所と知るべきことが離れているときのもの。

一件の形（`## ` で始まる題の下に、`対象:` と `確かめた:` の行と本文）：

```
## 題
対象: kernel/src/sys/sched.c, kernel/src/sys/events.c
確かめた: 2026-10-26 67bc115e
何を、なぜ。何で確かめたか。
```

対象はリポジトリからの道（glob 可、末尾の `/` は下全部）。フックは、そのファイルに初めて触れたときに全文を出し、圧縮の後は一行の見出しだけを出す。その後に対象へ入ったコミットと未コミットの変更の数を添えるので、数があれば今のコードと照らしてから使う。違っていたら、その場で直すか消す。古い覚え書きは、無いより悪い。

## コードのつながり：どこに響くか

- 編集の直後に、フックがそのファイルに頼るファイルと、編集した関数を呼ぶ所を出す。会話の間にファイルごと・関数ごとに一度ずつ。名前だけで推した確からしさの低いつながりは出さない。
- 書く前に呼ぶ側を見たいときは自分で引く：`codegraph explore "<問いや名前>"`、`codegraph callers <関数>`、`codegraph impact <関数>`。MCP の `codegraph_explore` も同じ。サーバーが動いていない時の CLI は、先に `codegraph sync`。
- 索引に出ないもの：番号で引くシステム呼出し（`common/abi.h` の `SYS_*`）、QuickJS へ登録する表、生成した束縛、third_party。「呼ぶ所なし」は「無い」の証拠ではない。ABI の境界は自分で読む。
- 一回の explore は数万字になることがある。名前を挙げて問いを絞る。索引はどこを読むかを決める道具で、編集する所は原文を読む。

## 四つの問い

AGENTS.md の「進め方：四つの問い」と同じ。答えが模型の中身になる。

### 書く前に：「これは誰のものか。二つ目が来たら、呼ぶ側は変わるか。」

持ち主を間違えた線は、後の修理のたびに例外と但し書きを呼ぶ。二つ目のメーカー・装置・利用者が来たと想像し、呼ぶ側に一つ目の名前が残るなら境界の位置が違う。二つ目の作者が一つ目から写すことになる部分は、共通の側に置く。一二行を正当化するのに作文が要るなら、その行があるべきかを先に考える。境界の設計は、書き始める前に模型へ数行で書き、最終報告の頭にも載せる。ユーザーはそれを読んで方向を正せる。

### 直す前に：「原因はどこにありうるか。動いている参照と我々の差は何か。」

見当が無いまま読む範囲を広げると、文脈が埋まり、圧縮が早まり、判断が消える。成熟した上流より、我々の移植・接着・渡す値に誤りがある見込みが高い。動いている参照（前に動いた回、上流の呼ぶ側、仕様書、別の実装）と我々の差を並べると、それが次の一手の候補表になる。候補が絞れたら、`rg`・codegraph で場所を出し、原文と仕様を読んで直す。これが仕事の本体。コードで欠陥が見えたら、ログや撮影で確かめ直さない。修理の案には「原因を消すか、症状を隠すか」を問う。

### 区切りごとに：「物差しは、前の区切りより目的の方へ動いたか。」

物差しは、目的が叶ったときにユーザーが見て分かるもの（画面、操作の速さ、落ちるコマ、実機の挙動）。模型の説明が細かくなることや、内部の数が減ることとは別。区切り（ビルドと確かめの一回り、コミット、圧縮、ユーザーのいない 2 時間）で、ユーザーが見るものを同じ条件で、今の一つの媒体を窓付きの QEMU で見て取る。測るのは直した後で、直していないのに測る回を重ねない。動いていなければ、同じ方向の次の細かい改善ではなく、なぜ効かないかを説明の一番にする。

### 言う前に：「何と何を比べて、そう言えるのか。」

「直った」「速くなった」「回帰ではない」「前から」「別件」は、同じ条件で見た二つの版を言えるときだけ。比べた二つ（版、組んだ時刻、媒体、撮った環境）と限界を同じ文に書く。参照・前の回・今回の三つがそろうまでは判定を書かない。

## 文脈の使い方

- 広く読む仕事（上流の奥、仕様書、多くのファイルにまたがる調べもの）は、問いを一つ持たせたサブエージェントに回す。返してほしいのは結論と根拠の場所。前提の監査も含め、ユーザーの許可を待たずに回してよい（2026-10-25 ユーザー確認）。
- サブエージェントは Opus 5.5 か Sonnet 5.5。小さな仕事ごとに出さず、作業木を何十も作らない（2026-10-29、一つの会話で 50 回・58 の作業木）。実装を任せたなら、取り込む前に差分を自分で読み、同じ媒体で確かめる。
- 前提の監査には、模型とコードの場所だけを渡し、自分の結論は渡さない。結論を渡すと、確かめられて返ってくるだけになる。問いは「この模型の前提のうち、コードや観測と合わないものはどれか」。
- 我々の経路上のコードは、自分の目で詳しく読む。原因が一番ありそうな場所だから。

## 始まりと終わり

- 会話の始まり：フックが置き場所と、この作業場の最近の模型を数件知らせる。続きの作業なら、その模型を先に開き、中の事実は今のリポジトリと照らす。
- 圧縮・再開の後：フックが模型と記録を入れる。要約の次の一手へ進む前に、ユーザーの原文と自分の流れを並べて読み、模型を今に合わせる。
- 終える前に：目的を一行ずつ読み返し、それぞれを何で確かめたかを書く（静的な確認・ビルド・QEMU の画面とログ・実機はユーザー）。確かめていないものは未確認と書く。知ったことは覚え書きか、その場所の注釈に移す。自分が起動した QEMU は `quit` で止める。
