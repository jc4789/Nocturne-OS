# 作業の模型

## なぜ

長い作業で筋を失うのは、判断の材料が、決める瞬間に目の前に無いから。圧縮の要約は直前の細かい作業を一番詳しく残し、ユーザーの前の言葉、自分で覆した説明、別のファイルで決まった約束を落とす。本人が書く模型も本人の今の枠を写すので、枠と一緒にずれる。

2026-10-25 の 16 時間の会話では、ユーザーが伝えた観測が模型の二回目の書き換えで消え、自分の計測で覆した説明が十四時間後に一番へ戻った。2026-10-27 の 20 時間の会話では、31 回の圧縮の間、物差し（落ちるコマ、fps）を一度も測らずに編集を重ね、ユーザーの「止まって報告しろ」が四回続いた。

だから作業場を分け、書く人を分ける。フックは見せるだけで、止めない（例外は下の「返事の言葉」）。

| | 書く人 | 置き場所 | 目の前に来る時 |
|---|---|---|---|
| 模型 | 本人 | `.claude/mokei/<作業場>.md` | 圧縮・再開の後（フックが入れる）、自分で開いた時 |
| 会話の記録 | フック（事象から） | `.claude/mokei/<作業場>.jsonl` | 圧縮・再開の後、節目の促し |
| コードの覚え書き | 誰でも | `.claude/oboegaki.md` | そのファイルを読む・書く時 |
| コードのつながり | codegraph | `.codegraph/`（手元だけ） | 編集の直後、自分で引いた時 |

作業場の鍵は会話の識別子で、デスクトップのアプリでは再開しても同じ作業場が続く。置き場所は会話の始まりにフックが知らせる。

## 模型：今、頭に置く判断

形は自由。今の作業に要るものだけを書く。

- 目的：ユーザーの言葉のまま。言い換えると目的がずれる。
- 物差し：目的が叶ったときにユーザーが見て分かるもの（fps、落ちるコマ、実時間、画面）と、その今の値・基準の値・取った条件。
- 今の一番の説明（二番手があれば）、それぞれ何を見たら覆るか、何で確かめたか（その版のログ・画面・計測、または推測）。
- 原因のありか：我々のコードから順に。なぜそこか。
- 境界の設計なら、持ち主と境界。
- 次の一手：どの説明とどの説明を分けるか。

読み返せる長さに保つ。自由に書き換えてよい。フックがすべての版を記録に残すので、消した説明も後から辿れる。済んだ作業の一覧や事実の写しは要らない。説明を「説明」を含む見出しの下に置くと、その一行目が版の流れとして圧縮の後に並ぶ。

## 会話の記録：フックが書くもの

本人は書かない。`.claude/hooks/mokei.py` が一行一事象の JSON で残す：ユーザーの発言（原文。ハーネスの通知やサブエージェントの報告は数えない）、模型の版、編集したファイル、計測（serial.log・撮影・試験・QEMU に触れたシェルのコマンド）、圧縮、自分の返事の頭、促し。

圧縮・再開の後に、フックが次を一度に入れる：

- 頭の一行：圧縮の回数、ユーザーの最後の発言からの時間、**最後に測ってからの時間とその間の編集の数**、説明の入れ替わりの回数。
- ユーザーの原文（最初のものと最近のもの。短い訂正はそのまま、落ちた分は一行の見出し）。
- 模型の版の流れ、編集の流れ（時間帯ごと）、最近の報告の頭、この会話の間のコミットと未コミットの変更。

要約をそのまま読むと、直前の作業へ戻りたくなる。記録は、自分の手間がどこへ行ったかを外から見せる。ユーザーの言葉と、版の流れ・編集の流れを並べて、同じ方向を向いているかを見る。向いていなければ、なぜそうなったかが今の説明の一番になる。「前から」「別件」と書きたくなったら、その判断がいつ何を根拠に模型へ入ったかを版で確かめる（`grep` で探せる）。

## 節目の促し

- ユーザーのいない時間が 2 時間ごとに一度、フックが節目を知らせる：何を測ったか・何が動いたか・次に何をするかの短い報告を書く、物差しが動かないなら同じ方向の次の一手へ進まない、自分が起動したもの（QEMU・ビルド・サブエージェント）を確かめる。
- 模型を書いてから編集が 40 件たまるごとに、模型を今に合わせるよう促す。
- 促しは一度ずつ。応じなくても止まらないが、記録に残る。

## 返事の言葉

Stop のフックが最後の返事を見て、日本語がほとんど無ければ一度だけ書き直させる（識別子・パス・コマンドはそのまま）。ユーザーに見える文はすべて日本語。

## コードの覚え書き：次に触る人が知らないと困ること

コードを読んでも分からないことを苦労して知ったときに書く。ファイルをまたぐ暗黙の約束、落とし穴と確かめ方（この経路は QEMU では通らない、この道具は失敗しても成功を返す）、文書の古い箇所。一か所で完結する約束はその場所の注釈に書く。

一件の形（`## ` で始まる題の下に、`対象:` と `確かめた:` の行と本文）：

```
## 題
対象: kernel/src/sys/sched.c, kernel/src/sys/events.c
確かめた: 2026-10-26 67bc115e
何を、なぜ。何で確かめたか。
```

対象はリポジトリからの道（glob 可、末尾の `/` は下全部）。フックは、そのファイルに初めて触れたときに全文を出し、圧縮の後は一行の見出しだけを出す。その後に対象へ入ったコミットと未コミットの変更の数を添えるので、数があれば今のコードと照らしてから使う。違っていたら、その場で直すか消す。古い覚え書きは、無いより悪い。

## コードのつながり：どこに響くか

- 編集の直後に、フックがそのファイルに頼るファイルと、編集した関数を呼ぶ所を出す。会話の間にファイルごと・関数ごとに一度ずつ。
- 書く前に呼ぶ側を見たいときは自分で引く：`codegraph explore "<問いや名前>"`、`codegraph callers <関数>`、`codegraph impact <関数>`。MCP の `codegraph_explore` も同じ。サーバーが動いていない時の CLI は、先に `codegraph sync`。
- 索引に出ないもの：番号で引くシステム呼出し（`common/abi.h` の `SYS_*`）、QuickJS へ登録する表、生成した束縛、third_party。「呼ぶ所なし」は「無い」の証拠ではない。
- 一回の explore は数万字になることがある。名前を挙げて問いを絞る。索引はどこを読むかを決める道具で、編集する所は原文を読む。

## 四つの問い

AGENTS.md の「進め方：四つの問い」と同じ。答えが模型の中身になる。書く前に持ち主を問う。直す前に、動いている参照と我々の差を並べる（それが次の一手の候補表）。区切りごとに物差しを同じ条件で見る。言う前に、比べた二つと限界を同じ文に書く。

## 文脈の使い方

- 広く読む仕事（上流の奥、仕様書、多くのファイルにまたがる調べもの）は、問いを一つ持たせたサブエージェントに回す。返してほしいのは結論と根拠の場所。前提の監査も含め、ユーザーの許可を待たずに回してよい（2026-10-25 ユーザー確認）。
- 前提の監査には、模型とコードの場所だけを渡し、自分の結論は渡さない。問いは「この模型の前提のうち、コードや観測と合わないものはどれか」。
- 我々の経路上のコードは、自分の目で詳しく読む。

## 始まりと終わり

- 会話の始まり：フックが置き場所と、この作業場の最近の模型を数件知らせる。続きの作業なら、その模型を先に開き、中の事実は今のリポジトリと照らす。
- 圧縮・再開の後：フックが模型と記録を入れる。要約の次の一手へ進む前に、ユーザーの原文と自分の流れを並べて読み、模型を今に合わせる。
- 終える前に：目的を一行ずつ読み返し、それぞれを何で確かめたかを書く（静的な確認・ビルド・QEMU の画面とログ・実機はユーザー）。確かめていないものは未確認と書く。知ったことは覚え書きか、その場所の注釈に移す。
