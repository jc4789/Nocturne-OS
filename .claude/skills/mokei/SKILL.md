# 作業の模型

## なぜ外に書くか

長い作業で失われるのは事実ではなく判断。圧縮の要約にはファイル名と概念の目録が残るが、「なぜこの説明が一番か」「何を見たら覆るか」「次の一手が何を分けるのか」は残らない。判断が消えると、圧縮のたびに同じファイルを読み直し、順位の無い仮説の一覧を作り直す。外に書いた判断は圧縮を越えて残り、読み返すたびに同じ場所から考えを再開できる。

ただし外に書いた模型は、ずれを隠すこともできる。2026-10-25 の 16 時間の会話では、ユーザーの発言が無いまま圧縮が 34 回あり、模型は 40 回書き換えられた。目的はユーザーの言葉のまま残り、Floorp の基準の値も毎回写された。それでも今の値は一度も書かれず、次の一手は、内部の計測の上位から一つずつ、互いに関係の無い細かい改善を渡り歩いた。書き換えのたびに説明は細かくなり、模型は良くなったように見えた。ユーザーが戻って見たのは、目に見える改善の無いまま入った退行三つ（題名の字体、頁の読み込み、WebGL の 7 から 2 fps）だった。模型が測っていたのは理解の細かさで、目的への距離ではなかった。

だから模型の中心は、目的を測る物差しに置く。

## 模型の書式

置き場所は、会話の始まりにフックが知らせる `.claude/mokei/<会話の識別子>.md`。知らせが無い環境では `.claude/mokei/` に作業の名前で作る。この場所は git に入らず、ユーザーも開いて読める。

```
# 目的
ユーザーの言葉のまま。言い換えると目的がずれる。複数あれば一行ずつ。
# 物差し
目的が叶ったら、ユーザーは何を見て分かるか。それを何で測るか（どの操作・どの条件）。
基準の値と、今の値（いつ・どの版・どこで：QEMU／Hyper-V／実機）。
守るもの：壊してはいけない既存の動きと、それを最後に確かめた版。
# 形
関わる部品の持ち主と境界。誰が決め、誰が実行し、誰が状態を持つか。
# 今の説明
一番もっともらしい説明を一つ、二番手があれば一つ。それぞれに「これを見たら覆る」観測を添える。
覆った説明は一行ずつ：何を見て覆ったか。
# ありか
原因がありうる場所を、我々のコードから順に。なぜそこか。
# 次の一手
物差しのどれを動かすはずの一手か。どの説明とどの説明を分けるか。結果がどちらなら何をするか。
```

十〜二十行に収める。追記ではなく書き換える。済んだ作業の一覧は書かない。それは git の履歴にあり、模型に置くと、物差しの代わりに作業の量が進み具合に見え始める。

ただし覆った説明は消さず、「今の説明」の下に一行で残す：何を見て覆ったか。消すと、数回の圧縮の後に同じ説明が新しい顔で戻ってくる。16 時間の会話では、16:41 に自分の観測で覆した説明が、06:32 に元の形で一番に戻っていた。目的に直接かかわる案（並列化の依頼なら、重い仕事を複数の CPU へ分ける案）を外すときも、外す理由を一行残す。理由の無いまま消えた案は、目的からそれた跡になる。

覆る観測は、結果を見る前に書き、結果を見た後に換えない。数が出てから「覆る観測」の方を書き換えたくなったら、それは説明が覆った合図。条件つきの次の一手（「〜が多ければ〜」）も、書き換えで条件を落とさない。

物差しが書けないなら、目的をまだ分かっていない。目的の言葉からユーザーが見るものを一つ選び、選んだ理由を書く。選べなければユーザーに聞く。「並列化が無い」なら、ユーザーが見ているのは CPU の使われ方と待ち時間で、内部の呼び出しがどの CPU で済んだかではない。

模型の判断には、何で確かめたかを添える（その版の QEMU の画面・ログ・計測・推測）。確かめていないものは「未確認」と書く。模型に書いた推測は、次の圧縮の後には事実の顔をして読まれる。16 時間の会話では、途中の版から出ていた不具合が「既知の別件」と書かれ、数回の圧縮の後には「以前から」になっていた。

書き換える時：観測が来たとき（ビルド・ログ・画面・ユーザーの報告）と、次の一手を選ぶ前。

## 四つの問い

### 書く前に：「これは誰のものか。二つ目が来たら、呼ぶ側は変わるか。」

持ち主を間違えた線は、後の修理のたびに例外と但し書きを呼ぶ。画面の保持が装置の占有の付属物になっていたときは、逃げ道と時間切れと長い注釈が七回積み重なった。設定の値をアプリが自分で書いて起動時に読み戻す形だったときは、変えた瞬間には何も効かなかった。

確かめ方：二つ目のメーカー・装置・利用者が来たと想像する。呼ぶ側のコードに一つ目の名前が残るなら、境界の位置が違う。二つ目の作者が一つ目から写すことになる部分があれば、それは社に依らないのに社の部品の中にあるもので、共通の部品の側に置く。一二行を正当化するのに作文が要るなら、その行があるべきかを先に考える。

境界の設計は、書き始める前に模型の「形」に数行で書き、最終報告の頭にも載せる。ユーザーはそれを読んで方向を正せる。

### 直す前に：「原因はどこにありうるか。動いている参照と我々の差は何か。」

ありかの見当が無いまま読む範囲を広げると、文脈が埋まり、圧縮が早まり、判断が消える。成熟した上流より、我々が書いた移植・接着・我々が渡す値に誤りがある見込みの方が高い。だから我々の経路上のコードから読む。

動いている参照を一つ選ぶ：前に動いた回、上流自身の呼び出し側、仕様書、別の実装。我々との差を並べ、効きそうな順に一つずつ消す。差の一覧を作ったら、それが次の一手の候補表になる。

修理の案を出すときは「これは原因を消すか、症状を隠すか」を問う。戻り道・時間切れ・逃げ道のキーを製品に足す修理は、原因を残したまま症状を隠し、次の調査の手がかりも消す。

### 区切りごとに：「物差しは、前の区切りより目的の方へ動いたか。」

区切りは、ビルドと試験の一回り、コミット、圧縮、そしてユーザーが長く見ていない時間。

説明が細かくなり、次の一手が具体的になることは、目的に近づくことと別。一つずつ測れば正しく見える改善が、目的の物差しでは見えない場所にあることは多い。だから区切りでは、模型の出来ではなく物差しの今の値を見る。

動いていないとき、あるいは今の値が古くて分からないとき、次の一手をそのまま続ける前に一つ選ぶ。

- 測る。同じ条件で今の値を取り、物差しに書く。測らずに次の改善へ進むと、動いていないことに気づく手段が無くなる。
- 説明を換える。「なぜ今までの改善が物差しに効かないのか」を今の説明の一番にし、それを分ける一手を打つ。動かないと書いた直後の次の一手が、同じ方向の別の細かい改善なら、それはずれの続き。
- 前提を監査に出す（下の「文脈の使い方」）。
- ユーザーに、今の値と、分かっていること・分かっていないことを模型のまま伝えて止まる。

ユーザーが居れば、苛立ちや訂正がずれを知らせる。居ない時間が長いほど、それをするのは物差しだけになる。

一回りに入れる変更は、物差しの差がどの変更のものか言える大きさにする。いくつもの変更を一つの媒体に束ねると、物差しが動いても動かなくても、どれが効いたか、どれが壊したかを言えなくなる。共通の層を変えるほど、「守るもの」の組を広げる。

### 言う前に：「何と何を比べて、そう言えるのか。」

「直った」「速くなった」「回帰ではない」「前からある」「別件」は、比べた二つを言えるときだけ言える。比べるのは、同じ操作・同じ条件で見た二つの版。片方しか見ていないなら、言えるのは見たことだけ。

報告にも模型にも、比べた二つと条件を同じ文に書く（「b2f5b721 を今日ビルドした媒体を QEMU で今日のサイトに当てても同じだった。今の媒体ではまだ見ていない」）。ユーザーはそれで言い分を確かめられる。会話の停止の後に「16 時間より前からの既存の欠陥であることが分かりました」と書いたときは、今の版を撮っておらず、比べた媒体のことをユーザーに説明もしていなかった。

## 文脈の使い方

- 広く読む仕事（上流の奥、仕様書、多くのファイルにまたがる調べもの）は、問いを一つ持たせたサブエージェントに回す。返してほしいのは結論と根拠の場所。この二種類の仕事と下の監査は、ユーザーの許可を待たずに回してよい（2026-10-25 ユーザー確認）。
- 我々の経路上のコードは、自分の目で詳しく読む。原因が一番ありそうな場所だから。
- 前提の監査：模型とコードの場所だけを渡し、自分の結論は渡さない。結論を渡すと、確かめられて返ってくるだけになる。問いは「この模型の前提のうち、コードや観測と合わないものはどれか」。
- 監査は関門として使う。その前提の上に作った変更を媒体にしてユーザーへ渡すのは、結果を読んでから。結果を待たずに進めた監査は、記録にしかならない。同じ題目を何度も監査に出しているなら、監査が測ることや作ることの代わりになっている。

## 終える前に

目的を一行ずつ読み返し、物差しの基準と今の値を並べ、それぞれを何で確かめたかを書く（静的な確認・ビルド・QEMU の画面・実機はユーザー）。確かめていないものは未確認と書く。

模型は作業の道具で、記憶ではない。残す価値があるのは、境界・持ち主・その理由の決定だけ。それはコードの注釈や ABI の文書へ移す。

## 圧縮の後

圧縮は続きの合図ではなく区切り。要約は直前の細かい作業を一番詳しく残し、「そのまま再開する」ように書かれているので、そのまま読むと直前の作業へ戻りたくなる。フックは目的と物差しと、この会話の圧縮の回数、ユーザーの最後の発言からの時間、模型が前の区切りの後に書き換えられたかを見せる。先に「区切りごとに」の問いに答え、それから模型ファイルで次の一手を読む。次の一手が物差しのどれも動かさないなら、続ける前に選び直す。模型が要約より古いなら、要約の次の一手に従う前に模型を今に合わせる。古い模型と新しい要約が食い違ったまま進むと、どちらの判断でもない行動になる。

模型が無い、または物差しの欄が無いなら、要約から目的を拾い、物差しを書いてから進む。
