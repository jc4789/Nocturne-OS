# ブラウザーを比べて確かめる

## なぜこうするか

- 2026-10-16：参照と並べずに判断し、関連動画の列とチャンネル情報が欠けた画面を「正常」と言った。どう見えるべきかを決めるのは、動いているブラウザーの画面。
- 2026-10-26：16 時間の性能の作業を、一つのサイトと固定の試験ページだけで確かめ、三つの退行（見出しの字体と大きさ、頁の部品が組み上がらず画像の取得が失敗、毎コマ描く WebGL が 7 fps から 2 fps）を入れた。どれもユーザーの Hyper-V で初めて見つかった。同じ日、退行を「（サイト名）の読み込み」と書いて正された。サイトを主語にすると、考えも調べる先もサイトの作りへ寄っていき、特例へつながる。
- 2026-10-27：20 時間の性能の作業で、ブラウザーが出している `Native media timing` の落ちるコマの数と描画の計測の行を一度も読まず、推測と一枚の撮影で判断した。計測の旗（`--debug-js`）を付けた回の数字で速さを語った。
- 2026-10-29：「変更前の基準を取る」を、旧版から組んだ媒体、ラベルの写し、`build/qa/hikaku/` の記録フォルダー、窓なしの QEMU で実装した。ユーザーは build/ を丸ごと消し、媒体は一つ、増分で組む、窓なしは禁止、qa のフォルダーを作らない、と言った。同じ日、七つのサイトを Floorp の参照でなく前の回の Nocturne の画像と見比べて「確かめた」と報告した。前の回の Nocturne は、どう見えるべきかを示さない。欠陥が「前から」で固定されるだけ。

## 道具はそれぞれ一つ

- **媒体は `build/nocturne.img` の一つ。** 変えたら `qemu-image` の増分ビルドで同じファイルを上書きする。写し・保存・ラベルの媒体・旧版から組んだ媒体を作らない。「前」とは、組み直す前にこの一つで撮って書き残した記録のこと。媒体ではない。
- **QEMU は窓付きで一台。** 起動、窓が出たことの確認、HMP での撮影と操作は `nocturne-project` スキル。窓なし（`-display none`、`scripts/test.py`・`platform_qa.py`・`wpt.py`）は使わない。
- **参照は Floorp の画像。** 前の回の Nocturne の画像は参照ではない。
- **置き場所。** 撮った画像と serial.log は、この会話の作業場（システムプロンプトにある scratchpad の場所）に置く。build の下に記録のフォルダーを作らない。残す値は台帳 `docs/browser/LEDGER.md` に文章と数字で書く。

理由：ユーザーの PC は一台で、二台目の QEMU や写しの媒体は重く、ディスクを食う。写しが増えると、どれが今の媒体か分からなくなり、ビルドの規則の漏れも隠れる。

## 三つの問い

### 開く前に：「この組は、変更が触れたすべての層を通るか。」

- 基本の組は、参照フォルダーの `TEST SITES.txt` に並ぶ全部。ユーザーが中身を変えるので、毎回読む。
- それに、変更が触れた層を通る実サイトを足す。毎コマ描く canvas・WebGL、動画の再生、検索欄への入力と送信、長いページのスクロールなど。依頼で指定されたサイトも必ず入れる。
- 一つのサイトだけで終えない。直したかったサイトが直っても、他のサイトが一つでも悪くなれば退行。
- 組に入れるのは実在のサイトだけ。自作の HTML、ローカルの試験ページ、example.com は入れない。

### 判定する前に：「参照画像のこの部品は、Nocturne の画面のどこにあるか。」

- まず参照の部品を書き出す。段組み、上部の帯、ナビゲーション、左右の欄、見出しの字体・太さ・大きさ・折り返し、本文の字体、画像・アイコン・動画の枠、ボタン、余白、固定要素、スクロールした先の内容。
- 一つずつ Nocturne の画像で探す。欠ける、形が違う、大きさが違う、位置が違う。どれか一つでもあれば失敗。
- 日々入れ替わる中身（記事、投稿、広告、おすすめ）は違いに数えない。構造、字体、大きさ、配置は違いに数える。
- 判定は、自分で画像を開いて見て行う。保存しただけ、ログに例外が無いだけ、読み込みが終わっただけでは判定にならない。前の回の Nocturne の画像と同じに見えることも判定ではない。
- 画面と一緒に console の行を読む。動画のある頁なら `Native media timing` の `drop`・`starved`、前の頁の音が鳴り続けていないか、例外が無いか。画面だけを見て、落ちるコマ・裂け・鳴り続ける音を見落とした。
- 動画は、指定の動画が時間どおりに進み、音が出て、停止・シーク・再再生ができるまでを見る。19 秒の動画に 29 秒かかれば「遅延なし」ではない。
- HTML5test のような対応表のサイトは、下まで送って未対応の項目を読み、実装へつなげる。得点だけを報告しない。

### 書く前に：「この違いは、我々のブラウザーのどの層の欠陥か。」

- 層の例：取得（HTTP/2、受け取りの勘定、Worker 経由の取得）、HTML の解析、DOM と custom element・shadow DOM、CSS のカスケード、字体の選択と読み込み、配置、描画と合成、媒体の解読と提示、JS の API、待ちとスケジューラー。
- 主語はブラウザーの欠陥にし、サイト名は「再現は◯◯」と添えるだけにする。
  - 例：「頁の一部の部品が組み上がらず、画像の取得が受け取りの記憶の不足で失敗する（再現は Reddit）」
  - 例：「見出しの字体と大きさが変わった（再現は YouTube の題名）」
- 同じ欠陥が組の他のサイトに出ていないかを見る。全部に出るなら共通の層（字体、配置）。ある種類の部品を使うページだけなら、その部品の層。
- 直すのは、仕様と共通の境界。サイト名での分岐、特定の DOM を狙った特例、UA の偽装、注入した CSS・JS で「直った」画面を作らない。
- サブエージェントへ調べものを頼むときも、依頼文の主語はブラウザーの欠陥にする。

## 参照を用意する

- ユーザーの参照フォルダーは `C:\Users\cesta\OneDrive\Desktop\NOS BROWSER\WEBSITE PICS`。入っているのは、Floorp で撮った窓全体の画面（Floorp 自身の枠を含む。ファイル名がサイト）、`TEST SITES.txt`（URL の一覧）、同じサイトを順に開いた Floorp の性能記録（`*profile.json.gz`）、ベンチマークの結果の json。ユーザーが足したり差し替えたりするので、中身と撮った日は毎回確かめる。
- 参照が無い、古い、または幅で段組みが変わるページでは、自分で撮る。組み込みのブラウザー（`mcp__Claude_Browser__*`）で同じ URL を開き、`resize_window` で Nocturne の頁の表示域と同じ幅・高さにしてから撮る。比べるのは同じ幅どうし。
- 自分で撮った参照は、URL・幅と高さ・撮った日時と一緒に作業場へ置く。
- 参照のブラウザーはログインの状態が Nocturne と違うことがある。違えばそう書く。参照の画面は物差しであって、Nocturne の合格の証拠ではない。

## 進め方

1. 受入表を作る。サイトごとに、URL、参照画像、照合する部品、行う操作（下へスクロールして戻る、リンク、入力）、測る値。
2. **変える前に、今の媒体で組の全部を撮り、書き残す。** 画像と serial.log は作業場へ、値と行は台帳と模型へ。条件は 2560×1440、F12 の console を開いたまま、計測の旗なし（`--log-console` までは可）。これが次の回の「前」になる。前の回の記録が無いときは、退行かどうかは未確認と書く。前の値と行が手元にあるなら、前の版を組み直して測り直さない。
3. 直す。`qemu-image` で増分ビルドして同じ img を上書きする。動いている QEMU を HMP の `quit` で止め、同じ img で起動し直す（`snapshot=on` なので、新しい媒体がそのまま載る）。
4. 同じ条件で撮る。窓の大きさ、開く順、操作、秒数をそろえる。
5. サイトごとに参照（Floorp）と照合し、前の回の記録と並べる。結果は四つのどれか：参照と一致／参照と違い、前の回も同じ（前から）／参照と違い、前の回は一致していた（退行）／前の回の記録が無く、前からか退行か未確認。
6. 速さを同じ条件で測る（次の節）。
7. 違いを層に割り当てて、修理へ戻る。退行は、新しい機能より先に直す。直したら、もう一度組の全部を撮る。

## 速さを比べる

- 測るもの：毎コマ描くページは fps、読み込みは最初の本文が出るまでと落ち着くまでの実時間、操作はスクロールや入力の応答、動画は落ちるコマ（`Native media timing` の `drop`）と `starved`。どれも CPU の使い方（カーネルの `prof: cpuN …`）も一緒に見る。
- **旗の決まり。** 製品の速さは `--debug-js` なしで測る。`--debug-js` は原因を探す回に使い、その回の数字を製品の速さとして書かない（heap の census が heap 全体を歩く）。計測を足したら、その道具自身の費用（`Browser console profile` など）を分けて読む。
- fps は `Browser loop profile` の `draw` と `Browser damage profile` の `partial draw` の回数を wall で割る（`--debug-js` の回だけ出る）。旗なしの回では、動画は `Native media timing` の `presented` の増え方、それ以外は同じ操作の実時間で比べる。
- 前の回と今回は、同じ媒体の条件、同じ QEMU の条件、同じ秒数の範囲で測る。差が小さいときは回を重ね、ばらつきも書く。
- **どの変更で変わったかを探すとき。** 前の回の値とログが手元にあるなら、それと比べ、条件の違い（旗の有無など）を書く。前の測定が一つも無く、比べないと判断できないときだけ、疑わしい `.c` を一つ前の版に戻して増分で組み、同じ一つの媒体で測る。stash・revert・旧版から組んだ媒体・写しは使わない。
- Floorp の性能記録は、Firefox Profiler の処理済みの形式。Python の `json.load(gzip.open(...))` で読め、文字列は `shared.stringArray` に引く。サイトごとのプロセスはスレッドの `eTLD+1`、CPU 時間は `samples.threadCPUDelta`（単位は `meta.sampleUnits`）、頁の節目は GeckoMain の印 `Navigation::Start`・`DOMContentLoaded`・`Load`・`FirstContentfulPaint`・`LargestContentfulPaint`。
- 2026-10-26 の記録の百度百科は、Firefox でも読み込みに手間取った回で、普段の値ではない。基準に使うなら撮り直す。
- Floorp の測定は実機、Nocturne の測定は QEMU であることが多い。条件の違いを書いたうえで、差を倍数で書く。「普通」「他のブラウザーと同じ」とは書かない。
- 改善と呼べるのは、実時間と fps（動画なら落ちるコマ）が同じ条件で動いたときだけ。一つのサイトが速くなっても、他のサイトが遅くなれば退行。内部の数（往復の回数、関数ごとの標本）が減っても、実時間が動かなければ改善ではない。

## 書いて残す

サイトごとに、次を書く。

```text
再現の URL：
参照画像（絶対パス、撮ったブラウザー・幅・日時）：
今回の画像と serial.log（作業場の絶対パス、媒体を組んだ時刻とコミット、旗）：
前の回の記録（台帳の行か模型の値。無ければ「無い」）：
照合した部品と結果：
操作と結果：
console・serial の行（drop・starved・例外・描画の回数）：
速さ（前の回・今回・Floorp。条件）：
判定（一致／前から／退行／未確認）：
欠陥の層と、次に直す境界：
```

- 確かめていないものは、未確認と書く。
- Hyper-V と実機はユーザーの担当。そこでの結果を、QEMU の結果から推さない。
- 台帳は `docs/browser/LEDGER.md`。測った値、退行、受入表を更新する。画像は作業場に残り、会話が終われば消えてよい。残すのは文章と数字。
