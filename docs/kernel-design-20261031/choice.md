# 二つの案を比べて選んだ芯（承認のための一枚）

2026-10-31。案 A（芯を薄く、`a.md`）と案 B（毎コマの道を核の中に、`b.md`）を、依頼文 `brief.md` の物差しと脅威の模型で比べた。設計の紙で、実装は持ち主の承認の後。

## 1. 結論

土台は **案 A** にする。B から六つを取り込み、穴を三つ直す（4・5 節）。どちらの案も、最初の段で実機（7600X）の空間の往復の値段を測り、その値で線を引き直すと書いている。この段はそのまま一番目に置く。

A は、世に言う microkernel に近い形をしている。持ち主が前に心配した「同時の重さの下で切り替えが遅くなる」は、A 自身が一番の弱点に挙げている所と同じ。A はこれを次の三つで扱う。

- 道を貸す：毎事象の道で、ドライバーの空間を通らない。
- 席：量の仕事を CPU の区画に分け、違う空間を一つの CPU で細かく刻まない。
- 第 0 段で測る：負けた道は主体を合わせて直す。

A を選んだ決め手は危険の性質。A の危険（切り替えの値段）は最初の段で測れ、負けた所だけを直せる。B の危険（ring 0 の大きさ、黙った壊し、区切りの規律の破れ）は測れず、起きてから分かる。

## 4. 二人が別々に同じ形に着いた所

二人は互いの案を見ずに書いたが、芯の多くが同じ形になった。

- **CPU**：CPU ごとの期限の列（期限の早い順）と、群の予算で配る。周期の拍は無い。
- **時刻**：LAPIC の one-shot へ、その CPU の一番早い期限をじかに書く。起こしの装置を抽象する層は作らない。
- **核の作り**：核は横取りしない。短い区切りで走り、横取りの禁止を数える入れ子は無い。
- **記憶**：2 MiB の区画を種類ごと・持ち主ごとに分け、頁を動かさずに大きな頁を何日も保つ。
- **handle**：世代と使用の数で引く。静かな点で回収する形は使わない。
- **記録**：書き手一人の、型つきの輪。
- **やり取り**：共有の記憶の輪と、「眠っている」の印。印があるときだけ知らせる。
- **番号**：プロセスの番号と thread の番号は別の数。
- **最初の段**：空間の往復と割り込みの遅れを、実機で測る。

**正直に書くこと**：「期限の早い順＋予算＋受け入れの判定」と同じ形の級は、Linux にもある（SCHED_DEADLINE）。二人とも、締めの数学からこの形に着いた。一つの CPU で締めを利用率 100% まで守れるのは期限の早い順だけで、固定の優先では 69〜78% まで。この案での違いは四つ。

- 級の階層が無く、時間を配る道はこれ一つ。
- 周期は装置か中身から来る：固定の拍の画面なら帰線、VRR の画面なら絵の流れそのもの、ほかに音の周期と入力の報告の間隔。
- 予約を渡すのは窓の主体（画面と入力の権限を持つ所）。
- 入らない予約は断る。

形が似ていることは隠さない。採るかどうかは持ち主が決める（7 節）。

## 5. 選んだ芯：A に足す・直すもの

### B から取り込む

1. **網の規約は、使う主体の library に置く。** NIC の主体は流れの振り分けだけを持ち、ARP・DHCP・ICMP は小さな世話役の主体に置く。こうすると、パケットの道で主体をまたがない。悪い入力の解析も、同じ相手の TLS・HTTP をすでに解く主体に収まる。
2. **合成する時には、描き終わった絵だけを選ぶ**（VRR の画面では新しい中身が来た時、固定の拍の画面では締めの時）。 描き終わりの値を一度読み、間に合わない絵は前の絵のまま出す。遅いアプリが、他の窓や他の画面を待たせない。
3. **期限を運ぶ道を全部のやり取りに広げる。** A は「呼び出しで期限と予算を貸す」だけを持つ。これを伝言・輪の知らせ・利用者の錠にも広げる。利用者の錠の語には持ち主の thread を書き、待つ者の期限を持ち主へ渡す。一コマの仕事が多くのプロセスに分かれても、期限が途中で失われない。
4. **shell（taskbar・menu・窓の枠）を合成の主体から分ける。** 合成の主体が小さくなり、固まったアプリがあっても閉じる釦は動く。
5. **2 MiB の持ち主。** A の「種類ごとの区画」の中で、2 MiB の塊を一人の持ち主（群か主体）に配る。持ち主が終われば塊は丸ごと戻る。
6. **受入の線を数で決める。** 落ちたコマは、フリップの記録で数えて 0。期限の起こしから走り出すまでは、p99.99 で 20 µs 以下。

### 穴を直す

1. **乗っ取られた格納庫が NVMe の管理の命令を書ける**（A の弱点）。NVMe の管理の待ち行列の送り側を、IOMMU で「装置は読むだけ」（IR=1、IW=0）に写す。I/O の待ち行列の送り側も同じにする。装置がそこへ書けないので、I/O の読みで管理の命令を差し込めない。管理の doorbell は格納庫に渡さない（A は register ごとの権利なので、もともと渡らない）。
2. **MWAIT の起こし語**（B の主張の誤り）。Zen 4 の MWAIT は C1 までしか入らない。起こし語が効くのは C1 で待つ CPU だけ。急ぎを受け持つ CPU は C1 で待ち、起こし語で起こす。それ以外の CPU は、次の期限までの間で眠りの深さを選ぶ（A の作り）。深く眠った CPU は IPI で起こす。
3. **固定した記憶の先取り**（B の弱点 6、A にも残る）。y-cruncher が先に固定すると、後から来たゲームが固定の記憶を取れない。固定できる量に群ごとの上限を置き、持ち主が設定の窓で変えられるようにする。画面・入力・記録の口座は、A の保証でもともと守られている。

### 合成の約束（画面と表示の装置が知らせる本当の値を使う）

外の AI の合成の案（原文は `outside-compositor.md`）を照らして足した。似た機能を同じ機能として扱わない。

外の案のうち、VRR の画面には当てはまらない所が三つある。どれも固定の拍を前提にしているので、採らない。

- 「各画面が自分の時計を持ち、走査から逆算して締めを決める」：VRR の画面には自分の時計が無く、フリップが届いた時に走査が始まる。逆算する元が無い。
- 「VRR でも、意図に合わせて安定した拍を保つ」：固定の予定を強いることで、VRR の働きを消す。安定した拍が要る中身（動画）は、コマの時刻そのものが拍になる。
- 「もうすぐ出来る絵を少し待つ」：推しで出すのを遅らせる。出来た絵はすぐ出す。

**画面から読むもの**

- **モニターが送るもの。** 能力の申告と、抜き差しの知らせ。
  - 申告の出所：EDID の基本の塊、その後ろの CTA-861・DisplayID の塊、DP なら AUX で読む DPCD。
  - 申告の中身：扱える mode と拍、VRR の範囲（最小と最大の Hz）、HDR と色域。
  - 接続のたびにモニターごとに読み、推さない。
- **今のコード。**
  - `common/edid.h` は基本の塊の名前と mode だけを読み、後ろの塊（高い拍の mode、VRR の範囲、HDR）を読まない。
  - NVIDIA の道では、NVKMS が EDID を全部読んで mode を出し、VRR の能力も持つ（`ports/nvidia/nvkms_os.c` の `conceal_vrr_caps`）。
  - これからは、共通の読み手を後ろの塊まで広げ、VRR の範囲と色を合成の主体へ渡す。
- **拍そのもの。** 拍は GPU の表示の装置が作り、モニターはそれに従う。だから帰線とフリップの時刻は、推さずに表示の装置から読む。今の道は、表示の装置がフリップを行った時刻を、完了の知らせから読んでいる（`ports/nvidia/nvkms_kapi_rm.c`、`NV_DISP_NOTIFIER` の time stamp）。

**時刻の扱い**（前の版の「C を学ぶ」を直す）

- 前の版は「締めの前倒し C をフリップの記録から学ぶ」と書き、二つの違うものを混ぜていた。
  - 表示の時刻：表示の装置が知っていて、誤りが無い。
  - 我々の GPU の仕事の長さ（合成と、重い描画の下での横取りの待ち）：負荷で変わる。測るのはこれだけ。
- 直した形：我々が出した合成の仕事の始めと終わりを GPU の時刻で記録し、その値から画面ごとに C を決める。C があるのは固定の拍の画面だけで、VRR の画面には無い（下の VRR の節）。
- なぜ最善か：分かっている値を推すと、推しの誤りの分だけ余白が要る。600 Hz では、100 µs の余白が 1 コマの 6% になる。

**四つの違う道**（同じものとして扱わない）

| 道 | 何をするか | 費用 | 限り | 使う時 |
|---|---|---|---|---|
| 直接の走査 | アプリの絵を、head の主の層にそのまま出す | GPU の合成 0 | 全面で、絵の形と大きさが mode と合う時だけ | 全面のゲーム、全面の動画 |
| 表示の装置の重ね | 表示の装置が、走査の時に層を重ねる | GPU の合成 0 | 層の数・形式（動画の YUV など）・拡大の能力は装置しだいで未確認。KAPI は head ごとに層を持つ（`layerState[head][layer]`） | 動画の窓、窓が少ない時 |
| cursor の面 | 表示の装置が指の絵を重ねる。位置の register を書けば、次の走査で動く | GPU も合成も通らない | 今の道は 32×32 の A8R8G8B8 だけ（`ports/nvidia/display.c`）。装置は 256×256 まで持てる（NVKMS の cursor の能力 `maxSize`）ので、32×32 は我々の限り | 指はいつも |
| GPU の合成 | GPU で、全部の層を一枚に描く | 帯域と、ゲームの GPU の仕事を横取りする待ち | 変わった所だけを描く | 効果・変形がある時、層が多い時 |

- 道は合成の主体が毎コマ選ぶ。アプリとの約束（絵の流れと場面の変更）は、どの道でも変わらない。
- なぜ最善か：
  - **cursor の面。** ゲームが GPU を埋めていても、指は次の走査で動く。GPU の合成で指を描くと、横取りの待ち（未確認。数百 µs になりうる）がそのまま指の遅れになる。
  - **重ね。** 動画を重ねに置けば、ゲームが GPU を埋めていても、動画の画面は GPU の合成を待たない。同時の重さの物差しに直に効く。使えるかどうかは表示の装置が申告する能力で決め、使えなければ GPU の合成へ落ちる。

**VRR：固定の拍を決して強いない。ハードウェアに任せる**

持ち主の画面は三枚とも VRR に対応している。VRR の画面には、合成の主体も核も固定の予定を決して強いない（2026-10-31、持ち主：「We never force a fixed schedule for VRR. Respect hardware」）。

- **表示の装置が自分でやること**（RTX 4070 の NVDisplay。NVKMS の `nvkms-vrr.c`・`nvkms-evo3.c` で照らした）：
  - VRR を働かせた head では、走査の生成が「続けて回す」から「一回ずつ」に切り替わる（`HEAD_SET_DISPLAY_RATE` の `RUN_MODE_ONE_SHOT`）。フリップ（`RELEASE_ELV`）が届くと、絵が出来た時に走査が始まる。
  - 新しいフリップが来ないまま最小の拍の間隔が過ぎると、表示の装置が前の絵をもう一度走査する（`MIN_REFRESH_INTERVAL`）。間隔は、モニターが EDID で申告する最小の拍から決まる（1/fmin）。低い拍の繰り返しは装置がする。
  - 一番速い拍は mode の走査の時間で決まり、装置が守る。
- **我々がすることは一つ。** 新しい中身がある時に、それをフリップする。中身が変わらなければ何もしない。繰り返しと上限・下限は装置に任せる。合成の主体も核も、時計で拍を作らない。VRR の head には締めの前倒しも無く、中身が出来たらすぐ合成する。
- **場面ごと：**
  - **全面のゲーム**（直接の走査）：ゲームの present が、そのままフリップになる。
  - **全面の動画**：各コマを、その提示の時刻にフリップする。動画の速さが最小の拍より遅ければ、繰り返しは装置がする。こちらで倍数の拍を選ばない（前の版の「48・72・144 Hz に合わせる」は消した）。
  - **窓が多い机**：どれかの窓に新しい絵が出来た時、または場面が変わった時に、合成してフリップする。他の窓は、最新の出来た絵のまま載る。前の版の「固定の最大の拍で回す」は消した。正直な限り：前のフリップの走査が終わる前に出来た絵は、その走査が終わるまで待つ（280 Hz の画面で最大 3.57 ms）。これは装置の走査の時間で、こちらの予定ではない。
  - **指**：指の動きも新しい中身。VRR の画面では、cursor の位置を書くと同時に走査を始めさせる。装置はそれを持っている：cursor の即時の channel の更新に `RELEASE_ELV` を付ければ、窓のフリップなしで一回の走査が始まる（NVKMS の `nvkms-cursor3.c` の `ReleaseElvC5`）。走査の速さの上限は装置が守るので、8000 Hz の報告でも、走査は画面の最大の拍までにまとまる。
    - NVKMS 自身は、指が動いても 33 ms（30 fps）待ってから走査を始める（`nvkms-vrr.c` の `nvTriggerVrrUnstallMoveCursor`）。理由は、指に応えてフリップするアプリのフリップが、指の起こした走査の途中に着いて待たされること。この 33 ms は固定の予定なので採らない。指は、ほかに何も変わらない画面でも最大の拍で動く。
    - 正直な限り：アプリのフリップが、指の起こした走査の途中に着けば、走査の終わりまで待つ（280 Hz で最大 3.57 ms）。これは装置の走査の時間。
    - 外での裏付け：VRR の画面で、指だけの更新では走査が始まらず指がカクつく問題は、他の系でも報告されている（`grounding.md`）。
- **期限の予約。** VRR の head には帰線の拍が無い。合成の主体の期限は中身から来る（アプリの出した絵の提示の時刻、動画のコマの時刻）。予約の周期は、その流れの速さ。
- **VRR の無い画面**（ほかの人の機械）：拍は表示の装置の帰線から来る。帰線に合わせるのは、そのときだけ。
- **パネルのちらつき**（事実として置く）：OLED と VA のパネルは、絵の間隔が大きく揺れると明るさがちらつく（RTINGS の測り、`grounding.md`）。パネルの性質で、こちらで固定の拍を強いる理由にはしない。持ち主の画面のパネルの種類は未確認。

**残りの約束**（理由つき）

1. **絵の寿命。** 出した絵は変わらず、すべての画面と GPU が使い終わるまで書き直せない。二枚にまたがる窓は、画面ごとに違う時刻に取られる。正しさのための約束。
2. **場面の変更は束で一度に効く。** 半分だけ動いた窓を見せないため。
3. **入力。** 拍を待たずに届け、時刻と「次に間に合う提示の時刻」を付ける（VRR の画面では、今の走査が終わる時刻）。指の動きはまとめてよいが、釦とキーの上げ下げ、順のある身振りはまとめない。押した事実を失わないため。
4. **提示の返し。** 表示の装置の時刻で、アプリへ結果（出た／繰り返した／飛ばした）と実際の提示の時刻を返す。落ちたコマの理由は四つに分ける：アプリが遅い、GPU が混んでいる、合成が重い、表示の締めに遅れた（VRR の画面では、締めの代わりに「走査の途中だった」）。ブラウザーの requestAnimationFrame もこれを読む。「落ちたコマ 0」を、我々の推しではなく装置の時刻で示すため。
5. **変わった所だけを合成する。** 上の予算の表は、全面を合成する最悪の値のまま置く。

**測れる範囲**：光までの遅れは、外の測り具が要る。記録で測れるのは、表示の装置のフリップの時刻まで。

## 6. 作る順と、最初に測るもの

順は A の 7 節のとおり。第 0 段で、7600X の実機で次を測り、結果を画面に大きな字で出す（実機の観測は写真で読む）。

- syscall の往復
- 空間の往復（IBPB の有無で）と、その後の TLB の入れ直し
- timer から thread が走り出すまで（起きている時、眠りの深さごと、全 thread で AVX-512 を回す重さの下）
- MSI から主体の thread が走り出すまで
- IPI での撃ち落とし（1 から 11 の CPU へ）
- GPU の合成の提出から完了までと、重い描画の下での横取りの遅れ
- MBE・CAT の効き

閾値は A のとおり。入力は、空間の往復が 3 µs 以下で、8000 Hz の入力の道が一つの CPU の 5% 以下なら、別の主体のままにする。格納は、Windows の値の 90% 以上を CPU 2 つ以下で出せれば、別の主体のままにする。越えた道は主体を合わせて直す（NVMe を格納庫と一つに、HID を窓の主体と一つに）。核の中へは戻さない。

## 7. 持ち主が決めること

| 問い | 推し |
|---|---|
| A＋上の直しを芯の土台にするか | する |
| 期限の早い順＋予算の形を採るか（Linux に同じ形の級があることを承知の上で） | 採る。締めの数学から来る形で、ほかに締めを守る形が無い |
| 核の stack | CPU ごと（thread の数の物差しに効く。作りは難しくなる） |
| 網の規約の置き場所 | 使う主体の library |
| 主体へ入るたびの IBPB | 入るたびに打つ。第 0 段の値で見直す |
| 休止（S4） | まず S3 だけ |
| 固定の記憶の上限の既定 | RAM の半分。設定の窓で変えられる |
| 盗まれた機械への備え | 鍵の置き場の口だけ今決め、作るのは後 |
| VRR | 決まった（持ち主）：固定の拍を強いない。新しい中身をフリップし、繰り返しと上限・下限は表示の装置に任せる |
| 物差しの一番速い画面 | 1080p 1000 Hz（1 コマ 1.0 ms）に上げる。600 Hz の 1080p はもう売られていて、2026 年には 1000 Hz の 1080p も出ている（`grounding.md`） |

AGENTS.md の「PCID を前提にしてよい」は、PPR 56713 と食い違う（二人とも指摘した）。直すかどうかは持ち主が決める。
