## Nocturne とは

- GUI が先の独自の OS。カーネルと libc は C。UNIX・POSIX・Linux ではなく、持ち主はその三つを嫌う。移植するプログラムの側を Nocturne のネイティブ ABI（`common/abi.h`、仕様 `docs/nocturne-native-abi.md`）へ書き換える。
- 的は実機：Ryzen 5 7600X（Zen 4、6 コア 12 スレッド）、RAM 32 GB、RTX 4070。GPU は NVIDIA の RM を ring 3 のアプリのドライバー `nvrm` として動かし、Mesa が上に載る（カーネルは PCI の claim・DMA・割り込みの口 `kernel/src/dev/pciuser.c` を渡す）。GPU は支える対象で、決め打ちせず継ぎ目（抽象化の層）で支える。上の的は 2 ソケットの EPYC（論理 CPU 1024、NUMA、CXL のメモリー）。下限は Zen 4。後ろ向きの互換は持たない（BIOS・PIC・PIT・xAPIC・古い ABI の道を作らない）。
- Hyper-V 第 2 世代と拡張セッション（RDP）は要件。VM だけの処理は `kernel/src/vm/vm.h` の一つの入口の後ろに置く。QEMU と Hyper-V は試験の道具で、VM で通ることは実機で動く証拠にならない。
- ディスクは一台（C: に OS・アプリ・利用者）。格納庫（C: の形式）は `common/store/`（B+木の catalog、commit）と `kernel/src/fs/`。
- ブラウザーは多くのプロセスを使う（取得の `webfetch`、媒体の worker、保存の worker、JS の Worker）。プロセスと thread の数は多い。

## 持ち主の決まり（設計に効くもの）

- 原案で作る。Linux・NT・Darwin・BSD などの形を写さない。名前を変えても形が同じなら写し。どの OS のカーネルのソースも読まない（`D:\Programes\cloned repos` の中の OS のソースも、`D:\Programes\OS DEV INFO\rtl_bsd_drv_v1102.01\` も読まない）。GPLv2 だけのコードは入れない。
- 前の建て直しは持ち主に全部捨てられた。理由は名前ではなく、作りが Linux の形だったこと。捨てられた形：横取りの禁止を数える入れ子の数（preempt count）、実時間の予算の級と EEVDF の sched、process の番号を主 thread の番号にすること、epoch・RCU 風の静かな点で回収すること、割り込みを thread に回す作り、printk 風の一本の記録、clockevent 風の起こしの装置の抽象。名前を変えて避けるのではない。どの部品も「何のためにあるか」と「その形はどこから来たか（どの物差し・ハードウェアの事実・要件がその形を強いるか）」を書き、既知の OS がそうしているからという理由は使わない。結果が既知の形に似たら、似たと書き、物差しからその形が強いられる理由を示す。
- shim・スパゲッティ・決め打ちの上限・見回り（ポーリング）・一つの大きな錠・一つの CPU に寄せる仕事は使わない。抽象化の層は責務の本当の継ぎ目に、名と契約と、各側の本物の実装を持って置く。
- GUI が先：窓・合成・入力・GPU は第一級の利用者。どの変更も何も悪くしない。
- 設計は持ち主が言葉で承認してから実装する。この文書はその承認のための紙。

## 物差し（最低線ではなく、理の範囲で一番厳しい線。どれも同時に）

- 画面：1440p 三枚、一番速いもので 280 Hz（1 コマ 3.57 ms）、遅いもので 165 Hz（6.06 ms）。消費者向けの 1080p 600 Hz（1.67 ms）。合成はどの画面もそれぞれの時刻で毎コマ間に合う。1440p の一コマは 14.7 MB で、三枚を CPU で毎コマ合成すると書きだけで 9〜11 GB/s 要るので、合成は GPU（RTX 4070 は 504 GB/s）で。
- 入力：8000 Hz のマウス（報告の間隔 125 µs）。
- 同時の重さ：一枚の画面で AAA ゲーム、一枚で動画、一枚で SNS を同時に。カクつきも落ちるコマも 0。これは最低線で、Windows は当たり前にこなす。
- 計算：y-cruncher で全コアを何日も使い切る（1 兆桁の π の規模：数十 GB の固定した記憶、2 MiB の頁、直接の I/O、何日も安定）。その間も画面と入力は滑らか。作りが CPU の足を引っ張らない。
- 固まり：NVMe を飽和させても格納庫が固まらない。核の錠が詰まらない。
- 規模の四つの軸：時間（何日も動く）、量（数十 GB の固定した記憶、TB のファイル）、速さ（600 Hz、8000 Hz、飽和した NVMe）、数（1024 CPU、多くのアプリと画面）。

## これまでに話した芯の考え（出発点。良くできるなら変えてよい。変えたら理由を書く）

1. 脅威の模型を先に書く：何から何を守るか（悪意のある・壊れたアプリ、外から来たコード（ブラウザーの頁の JS・Wasm、移植したプログラム）、壊れたドライバー、装置の DMA、盗まれた機械）。
2. 境界は三種類：
   - 強制の核（enforcement kernel）：隔離の機構と期限の機構だけを持つ。
   - 主体の境界（principal boundary）：アプリや service ごとの別の番地空間と、最小の権限（capability）。
   - 区画の境界（compartment boundary）：主体の中の部分を分ける。既定は別プロセスの下位の単位。PKU（Zen 4 にある）は CFI がある所の補いとしてだけ。
3. 境界とは直交する方針：IOMMU、GPU の文脈、資源の予約の群（CPU・記憶・帯域を前もって確保する単位）、再起動の単位、身元、UI と入力の権限（誰が画面と入力を持つか）、起動と更新の信頼、秘密。
4. 速さの規則：毎コマ・毎事象の道で、操作ごとに主体の境界を越えない（共有の記憶の輪と、まとめた通知で）。
5. 決め手の問い（どこまで別の空間に出すか）は、理屈だけでなく実機で測って決める。何を最初に測るかを書く。

## ハードウェアの事実（照らしたもの）

- Zen 4（AMD PPR 56713）：PCID は無い（CPUID 1 ECX の PCID は Fixed,0）。INVPCID はある。PKU はある。x2APIC、不変の TSC。TSC-deadline の有無は未確認。AVX-512、XSAVES。
- 仕様書は `D:\Programes\OS DEV INFO`（AMD APM、PPR、PCIe、NVMe、xHCI、AMD IOMMU、ACPI など）。記憶でなくここで照らしてよい。

## 立場 A：芯を薄く

強制の核は隔離と期限の機構だけを持つ。装置のドライバー・格納庫・網・窓と合成は、それぞれ別の主体（別の番地空間）で動く。この立場を取ったうえで、速さの規則と物差しをどう満たすかを示す。この立場が物差しで負ける所が見つかったら、隠さずに書き、どう直すかを示す（立場を変える理由になるなら、そう書く）。

## 立場 B：毎コマの道を核の中に

毎コマ・毎事象の道にある service（装置のドライバー、格納庫、網、入力、表示の scanout と合成の制御）は核と同じ守られた空間に置き、その中の失敗の封じ込めと再起動を、別の番地空間に頼らずにどう作るか（区画・IOMMU・再起動の単位など）を示す。アプリと外から来たコードは主体の境界の外。この立場を取ったうえで、脅威の模型と物差しをどう満たすかを示す。この立場が負ける所が見つかったら、隠さずに書き、どう直すかを示す（立場を変える理由になるなら、そう書く）。
