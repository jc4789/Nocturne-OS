# NVIDIA / GPU 比較監査の修理（2026-10-20）

## 範囲と保全

`comparative-audit-20261020.md` の P1/P2 を対象に、Nocturne の native ABI・RM adaptation・NVK/Mesa・virgl・梱包を修理した。POSIX 互換層や他OSのドライバーは追加していない。`kernel-open/uvm_common.c` は参照・使用していない。vendor RM の変更は、MIT の `third_party/nvidia-open/src/nvidia/arch/nvalloc/unix/src/os.c` にある Nocturne 専用の user-map 寿命通知だけである。

開始時の `build.ps1`、`scripts/build.py`、`docs/nvidia/LEDGER.md` の差分は保全した。共有 ABI の既存 syscall 番号・固定 batch の1936-byte layout・RM Protocol1 の48-byte messageを維持した。新しい上限は導入せず、装置能力、表現幅、実メモリ、幾何学的境界を使う。

## 修理対応表

| 監査 | 修理した製品境界 | 重要な互換・寿命条件 |
|---|---|---|
| P1-1 RM 主体混同 | 接続ごとに再利用しない RM principal、request/cleanup の TLS 復元 | 認証済み peer PID の代用品とはせず、接続間の暗黙共有を拒否 |
| P1-2 RO 欠落 | native view の不可逆最大権利、RM の保護属性伝播 | 派生・転送・再mapで RW へ拡大不可。旧 client の RO→RW 要求は拒否 |
| P1-3 posted write | channel 専有 VRAM page の volatile BAR1 read、GPPut/doorbell 前後の fence | channel 解放前に drain page を解放しない |
| P1-4 virgl 待機 | MSI-X / native wait queue、非対応時は scheduler 粒度の待機 | DMA backing は timeout 時に再利用しない。待機中の user unmap は snapshot/copyout 再検査 |
| P2-5 BAR 配置 | PCI の有効 memory BAR 順序で aperture を構成 | register / USERMODE は UC、FB のみ WC。非prefetchable BAR の WC を拒否 |
| P2-6 RM エラー | transport と RM の関数返却 status を区別して伝播 | 旧 client も負の status で失敗を認識、新 client は NV_STATUS を取得 |
| P2-7 timeline 累積 | signal 追加・CPU signal 時の完了点回収 | 同一 fence / 同一 seqno だけ集約し、旧値待機を後続点へ遅延させない |
| P2-8 CPU screen 固定 | CPU/GPU screen を別保持、ready 後の新contextを再選択 | 生存中 CPU context の screen / clear 方式を変えない |
| P2-9 WebGL caveat | 選択 backend の accelerated capability で判断 | GPU 選択を実測高速化と呼ばない |
| P2-10 headless WSI | 広告・依存拡張・初期化条件を整合 | native 契約試験で広告から surface の生成破棄まで確認する |
| P2-11 複数 GPU | BDF endpoint / BDF 再open、動的 PCI 列挙 | 旧 default alias は一つ残し、alias 衝突で別GPU daemonを終了させない |
| P2-12 firmware 梱包 | 内容 hash manifest と initrd 依存、有効/無効切替、原子的 archive 置換 | 不完全 install を拒否。梱包する実データを照合し、失敗時は既存 archive 保全 |
| P2-13 人工描画上限 | 動的画像 resource、可変 triangle-list、PAGE_SIZE 単位の分割・yield | 旧APIを保持し、641幅・97三角形・従来範囲外座標を試験 |

条件付き指摘も修理した：RM の明示/暗黙 unmap と client close による正確な view 取消、取消scopeの派生継承、IRQ disable時のwaiter起床、complete-all型waitqueue、Cの引数評価順依存除去、停止を確認できないDMAの隔離。起動直後のBME操作を再導入していない。

## 独立レビューで修理を追加した点

- 親が旧 RM バイナリーの互換と暗黙 FREE の反例を提示。担当は Protocol1/alias を復旧し、物理addressではなく RM 所有の一意 token に native view の取消を接続した。
- 同じ物理addressを二重mapした試験は、一方の解放が他方を失効しないことを確認した。
- NVK 担当の独立レビューで firmware の GSP だけ欠落する install と、hash確認後から格納までの変更を検討。親が両方を拒否し、失敗時に既存tarを残す実装へ修理した。
- kernel 担当の第二検討で resource破棄opcode、横長/縦長履歴による過大capacity、scheduler待機後のユーザーbuffer寿命を修理した。親も syscall、共有scope、GPU資源、RM/IPC、NVKの実差分を読んだ。

## 検証記録

証拠は `build/gpu-repair-20261020/`。host mock、cross build、実 QEMU、NVIDIA実機は同じ合格として扱わない。

### ホスト・ビルド

- firmware：8試験成功。選択切替、無変更mtime保持、不完全install、同一mtimeの内容変更、TOCTOU、既存archive保全を含む。
- RM：実ソースを用いた3群成功。native handle / RM dispatcherはmock。追加した実7翻訳単位の単独target構文検査も成功。
- NVK同期：実同期ソースの完了点回収、参照数、旧seqno保持、binary置換を確認。Mesa frontendは新contextだけの昇格と旧context維持を確認。
- CPU描画：実clip/raster本体の境界・100000ケースを undefined-trap 付きで実行、成功。native syscall/GPU IOはこの試験の対象外。
- 統合ビルド初回で `rm_api.c` の定義header不足が判明し、正規headerの直接includeで修理。新native試験のリンクも通常アプリと同じ `--gc-sections` に揃え、未使用DRM経路のための互換関数を追加せずに修理した。
- 梱包途中で無出力のSYSROOT処理を停止疑いとして扱い、その後の一時物再生成が `Directory not empty` で失敗した。jobserver停止を確定原因とはしない。関連梱包処理の終了と解決済みbuild内パスを確認して、既存objectを保持した単一ジョブの正規増分ビルドへ切り替えた。

### 修正前 QEMU 基準

WHPX / 4CPU / 4096MiB / 1920×1080、AHCI boot、専用snapshot媒体、一台のみ。

- 標準VGA + edu：pcitest/nvrmtestは0失敗、GPUなしのgputestは35検査0失敗。CPU fallbackでありGPU成功ではない。
- virgl + `gpu-enable` + edu：backend1/caps15。pcitest/nvrmtest成功。gputestは43検査中 `blit-max-source-last-pixel` が1失敗。期待値を弱めず修正後に残した。
- 親が `baseline.png`、`baseline-browser-open.png`、`edu-before.png`、`virgl-before.png` を開いて目視。desktopとabout:homeの構成を確認。これらは修正後の成功証拠ではない。

### 修正後の実失敗と追加修理

- 最初のedu試験ではRO protectが1件失敗した。製品のVMMは正しく拒否しており、試験が便利APIの`-1/errno`とraw syscallの負エラーを混同していた。便利APIは`-1`かつ`N_ERR_DENIED`、rawは`-N_ERR_DENIED`を両方要求する試験へ訂正した。拒否条件を弱めていない。
- 元から失敗していた末端画素は、初回修理後も旧フレームの色が残った。COPY命令へ替える仮説も四隅・2×2で失敗し、棄却した。拡大は成功するという差と、独立MITライブラリーvirglrendererの座標契約を照合した。コードの取り込みはない。
- 最終修理ではGPU画像のwire原点を統一し、nativeの上原点描画はviewportの負Y scaleで変換する。等倍も拡縮もBLITの共通経路へ戻した。元の期待値を保持し、四隅・包含2×2・末端拡大・非対称上下向きの反例を追加した。

### 最終QEMU

WHPX / 4CPU / 4096MiB / 1920×1080、AHCI boot、一台ずつ、専用boot/dataのsnapshot。GPU条件は`virtio-vga-gl`・`gpu-enable`・edu、CPU条件は同じ装置構成で`nogpu`。CPU条件で同一のedu試験は反復せず、変更条件に必要な描画だけを確認した。

| 経路 | 実結果 | 証拠 |
|---|---|---|
| eduのnative PCI・DMA・IRQ・共有権利 | `pcitest: 0 failed`。RO拡大拒否、派生view取消、別appの既存map失効、owner map保持、IRQ disableでの無期限wait起床 | `origin-after-serial.log` |
| RMの不適合装置拒否 | `nvrmtest: 0 failed`。edu拒否後のclaim再取得 | 同上 |
| 一般GPU / virgl | backend1・caps15、**55検査・0失敗**。641幅、97三角形、旧ABI、範囲外座標、元の末端画素と追加反例を含む | 同上 |
| NVK/Mesa native契約 | **0件失敗**。拡張依存、instance/headless surface生成破棄、softpipeの赤/緑context保持 | 同上 |
| 一般GPUのCPU fallback | backend0・caps0、**44検査・0失敗**。可変要求を含むCPU描画 | `cpu-after-serial.log` |

取消後のchild読取りによるpage fault終了142は、試験が要求した隔離結果でありkernel crashではない。eduにはPCIe Transactions Pendingによる停止完了証明がないためDMAを隔離した。ログの「requests in flight」は実pendingを観測した証明ではなく、隔離が解除されたとも主張しない。

- IMG内と実QEMU用boot内のkernel/initrdを`mtype`から直接hashしてbuildと一致。VHD/VHDXは`qemu-img compare`でIMGと内容一致。
- ISO内kernel/initrdを`xorriso -compare`で照合。差は`-r`生成によるmode/uid/gidのみ、ファイル内容差なし。ISO stagingもbuildとhash一致。
- initrd内browser/init/nvrm、native/gpu ABIヘッダー、libc、firmware3点をbuild/source/選択manifestとhash一致。`delivery-integrity.log`は後半の参照パスを`build/bin`と誤ったため終了1だが、媒体照合の完了行は保持した。残りだけを正しい`build/root/bin`・sysrootで照合した`delivery-tar-integrity.log`は終了0。
- 今回のboot640MiB/data256MiBは全条件で一組を再利用。QEMU終了後、解決済みpath・非link/junction・非使用を確認してこの二ファイルだけを回収した。通常data、四配布媒体、ログ、画像、再現用設定は保全。回収後D空きは110.08GiB。削除済み試験媒体をそのまま再実行可能とはしない。

## 実機に残る検証境界

QEMU edu は Nocturne の PCI/IRQ/DMA/共有権利を検査するmock装置であり、NVIDIA GSP、実BAR1到達順序、実GPU DMA、複数NVIDIA GPU描画、ready後の実GPU昇格を検証するものではない。ホストvirgl rendererのNVIDIA製品名はNocturne RM/NVKの実行証拠ではない。native NVIDIA modeset/NVDEC の新規実装を今回の修理範囲に偽装していない。Hyper-V実機はユーザー担当。GPU転送・同期込みの速度改善は未測定。
