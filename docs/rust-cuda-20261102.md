# Rust と CUDA：ZLUDA、cuda-rust、CCCL をどう扱うか

2026-11-02 の調べもの。読んだのは今のコードと、各プロジェクトの公開の文書。どれも組んでおらず、実機でも動かしていない。

依頼（原文）：

> https://github.com/vosen/ZLUDA  cuda for non NVIDIA gpus, written in rust. And, cuda for NVIDIA gpus written in rust, https://github.com/NVIDIA/cuda-rust    with how popular rust has become, i think we we might need improve our support for it*(if its not good of course.).   Not sure Of your thoughts on this, and what the best path forward is from here.

> https://github.com/nvidia/cccl

## 結論

- Rust は直す。理由は CUDA ではない。今の Rust のプログラムは、このリポジトリの中でしか組めない。
- ZLUDA、cuda-rust、CCCL は今は移植しない。三つとも CUDA の利用者側のドライバー（`libcuda`）の上に立つか、その代わりを AMD の HIP に頼る。Nocturne にはどちらも無い。
- GPU の計算の第一の道は Vulkan のまま。Rust からも同じ道を使う。
- Nocturne 自身の `libcuda` を作る案は、作るならこの形という設計だけを残す。要るプログラムが出たときに決める。

## 三つのプロジェクト

| | 何か | 動くのに要るもの | Nocturne では |
|---|---|---|---|
| ZLUDA | CUDA の代わりの実装。変更なしの CUDA のアプリを NVIDIA 以外の GPU で動かす。Apache-2.0 か MIT。 | `zluda` の crate は `hip_runtime-sys`。Windows の手引きは AMD のドライバーと HIP SDK を求める。読み込みは Linux の `LD_LIBRARY_PATH` か `LD_AUDIT`、Windows の `zluda.exe` か `nvcuda.dll`。 | AMD のドライバーが無い。HIP も無い。読み込みの仕組みは Linux と Windows の形で、持ち込まない。 |
| cuda-rust | NVIDIA の Rust の CUDA。host 側の crate と、核を Rust で書く二つの道。`cuda-oxide` は Rust から PTX。`cutile-rs` は Rust から Tile IR を経て cubin。Apache-2.0。作者の言葉で early-stage research project。 | `cuda-oxide` は `libcuda` を実行時に読み、CUDA 13.x のドライバー（R580 以降）と CUDA Toolkit 13.0 以降を求める。試された OS は Linux。`cuda-bindings` の組みは Toolkit の見出しから作り、探す場所は Linux と Windows だけ。 | `libcuda` が無い。PTX を機械語にする部品も無い。 |
| CCCL | Thrust、CUB、libcudacxx。全部 header。 | CUDA の backend は `nvcc` と CUDA の実行環境。Thrust の別の backend は TBB と OpenMP。対応の OS は CUDA Toolkit と同じ。 | header は問題にならない。CUDA の backend は `libcuda` が要る。TBB と OpenMP は `ports/` に無い。 |

ZLUDA の Q4 2025 の報告：llama.cpp は全面的に動き、速さは ROCm の backend とほぼ同じ。PyTorch はまだ。

## 欠けは一か所

```
CCCL、cuda-rust の host、CUDA の backend を持つプログラム
  │ cu* の呼出し
  ▼
[無い] CUDA の利用者側のドライバー（NVIDIA は Linux と Windows の閉じた libcuda を出す）
  │                         │
  │ RM と UVM               │ PTX から機械語
  ▼                         ▼
[ある] nvrm               [無い] NVIDIA の変換は閉じている
```

閉じたライブラリー（cuBLAS、cuDNN）は Linux と Windows の binary で、Nocturne は読み込まない。Linux の ABI は足さない。PyTorch の CUDA 版が要るのはこれらで、`libcuda` を作っても届かない。

## 今の Rust の状態

読んだ結果。`rusttest` の 49 項目は QEMU で通る。

動いているもの：

- `std` はネイティブの ABI の上にあり、`libc` の crate も `target_family = "unix"` も使わない。
- NAK と `nil` はこの `std` で組まれ、GPU のドライバーの像に入る。Rust の移植はすでに GPU の道の一部。

欠けているもの：

| 欠け | 今 | 大きさ |
|---|---|---|
| cargo で組めない | アプリは `ports/rust/apps/<名>/main.rs` の一ファイルで、`rustc-nocturne.sh` が組む。crate を使えない。 | 中 |
| SDK に無い | `scripts/mksdk.sh` は sysroot も標的の定義も入れない。 | 中 |
| 窓を開けない | `nocturne.h` の Rust の binding が無く、`std::os::nocturne` も無い。手で `extern "C"` を書く。 | 中 |
| `std::net` | 未対応。`tcp_connect`、`tcp_listen`、`tcp_accept`、`udp_*` は libc にある。 | 小 |
| `std::process::Command` | 未対応。`n_app_launch` は libc にある。パイプは無く、channel を使う。 | 小〜中 |
| `Builder::stack_size` | 効かない。`thread_create_sized` は libc にあり、カーネルにスレッドの数の上限は無い。差分のコメントの「128 本」は古い。 | 小 |
| `panic=unwind`、バックトレース | 無い。`catch_unwind` は捕まえない。`libunwind.a` と `.eh_frame` の置き場は C++ のためにある。 | 中 |
| `current_exe`、`is_terminal` | 無い。 | 小 |
| 外の crate | `mio`、`socket2`、`memmap2`、`libloading` などは OS ごとの実装を持つと考えるが、一つずつは確かめていない。`libc` の crate は持ち込まない。 | 使うものごと |
| OS の中で組む | `rustc` と `cargo` は Nocturne の中に無い。`Command` と proc-macro の読み込みが要る。 | 大 |
| 版の追従 | Rust 1.98.1 に固定。標的は JSON で `RUSTC_BOOTSTRAP=1` を使う。`cuda-oxide` は 1.99.1 に固定。 | 版ごと |

標的は `cpu: x86-64`、C は `-msse2` で組んでいる。AGENTS の下限は x86-64-v4 で、上げたときの速さの差は測っていない。

## 言語によらないシステムの欠け

文書を記憶へ写す口が無い。`n_document_load` は全部を新しい頁へ読む。`n_pager_*` はあり、これで作れるかは設計していない。LLM の重みは何十 GiB にもなる。

`docs/gpu-compute-20261102.md` の「大きな計算で先に当たりそうな所」もそのまま残る。

## Rust から GPU へ

| 道 | 形 | 状態 |
|---|---|---|
| Vulkan を直接呼ぶ | Rust の binding から libc のローダーへ。 | 組んでいない。`ash` が Nocturne で組めるかは確かめていない。 |
| CubeCL（Burn が使う） | Vulkan は SPIR-V の compiler と wgpu。MIT か Apache-2.0。 | 作者の言葉で alpha。Nocturne でも NVK でも試していない。wgpu の依存の移植が要る。 |
| rust-gpu | rustc の backend で Rust から SPIR-V。MIT か Apache-2.0。 | 作者の言葉で early stage。NVK で試していない。 |

## 進める順

1. **ユーザーの試しで見つかる不具合。** 退行は新機能より先。
2. **窓なしの Vulkan の計算を実機で走らせる。** `tests/computetest.c`。小さい計算の次に大きな確保まで広げる。
3. **Rust の土台。**
   - `std`：`stack_size`、`net`、`Command`、`current_exe`、`is_terminal`、`panic=unwind`。
   - 組み：SDK に sysroot と標的を入れ、外のフォルダーで `cargo build` が通る形にする。
   - 口：`nocturne.h` から binding を生成する crate と `std::os::nocturne`。窓を開く Rust のアプリを最初の呼ぶ者にする。
   - 2 の試験の Rust 版で、Rust から Vulkan の計算まで通す。
4. **文書を記憶へ写す口。** 持ち主は `mm/` と `fs/`。設計してから見せる。
5. **像の表の継ぎ目。** `docs/gpu-compute-20261102.md` の案 1〜3。
6. **外の crate。** 使うものが決まってから一つずつ足す。

## 作るならこの形：Nocturne の `libcuda`

条件：Vulkan で届かず、ソースがあり、人が使いたいプログラムが出ること。今は条件を満たしていない。

- `nvrm` の client として、像の中に `cu*` を実装する。継ぎ目は `"nvidia.rm"` と同じ場所。特権の半分（RM、UVM）はある。カーネルは変えない。
- PTX は `ptx_parser`（ZLUDA、MIT か Apache-2.0）か自前で読み、NIR へ変え、NAK で機械語にする。全部が開いた部品になる。NAK の出す機械語の速さは NVIDIA の変換と比べていない。ZLUDA の `ptx_parser` のコードは読んでいない。
- 開発の機械の `ptxas` で作った cubin を読み込む道もある。cubin の書式に作った者の公式の文書があるかは確かめていない。
- これで届くもの：CCCL、cuda-rust の host と `cuda-oxide`、cuBLAS と cuDNN を使わない CUDA のプログラム。
- 届かないもの：PyTorch の CUDA 版など、閉じたライブラリーに頼るもの。
- 確かめていないこと：NVIDIA の Toolkit の見出しと道具の使用条件。

AMD の GPU で動かす話は別の仕事で、まず Nocturne の AMD のドライバーが要る。
