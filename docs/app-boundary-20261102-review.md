# プログラムと OS の境界：設計の読み直し

対象は [境界の設計](app-boundary-20261102.md) です。実装を始める前に、今のコードと照らして読みました。設計の本文は、この結果に合わせて直してあります。

## 判定

- **方向には同意します。** 入口、静的な libc、サービスの線、世代、Vulkan は正しいです。
- **そのままでは組めない点と、境界が混ざる点がありました。** 全部で十一です。
- **一番悪いのは GPU の部分でした。** ユーザーも同じ判断でした。一般の「封じた module」をやめ、GPU のドライバーの像だけの狭い形にしました。

## 組めない点

| # | 元の案 | 問題 | 直し |
|---|---|---|---|
| 1 | 像は「関数の表」、書込みなし、再配置なし、番地はプロセスごと、frame は共有 | 同時に成り立ちません。関数の番地を並べた表は再配置が要ります。 | 表をやめ、16 バイトの溝を番号の順に並べます。呼ぶ番地は `entry + 番号 × 16` です。 |
| 2 | 溝の外の時計の扱いが書かれていない | `struct n_clock` の形と `N_CLOCK_ADDRESS` が ABI に残ります。監査の欠陥 1 が半分残ります。 | 時計を読むコードを像の中へ移します。データは像の直後に写し、プログラムからは形が見えません。 |
| 3 | 封じた module のスレッド局所は「未設計」 | 足し物ではなく、組めるかどうかの問題です。libc は `%fs:0` を読み、TLS は `%fs` からの負の距離です。二つの libc が一つの `%fs` で衝突します。 | `%fs:0` を ABI の `struct n_thread_block` にします。libc の写しは自分の記録を区画に繋ぎます。 |
| 4 | `Makefile` の組みに触れていない | 全部が `-fno-pic` で、LLVM は `LLVM_ENABLE_PIC=OFF`、Rust は `relocation-model: static`、`tls-model: local-exec` です。「普段の開発に手間を足さない」は成り立ちません。 | 像に入る object（libc の核、Mesa、NVK、Rust）だけを PIC にし、同じ object をプログラムにも使います。lld が静的なリンクで元へ緩めます。組みは二重になりません。 |

## 境界が混ざる点

| # | 元の案 | 問題 | 直し |
|---|---|---|---|
| 5 | 「syscall の番号は像の中に閉じる」 | `表[番号]` の番号はプログラムに残ります。番号の置き場が変わるだけです。 | そう書きます。溝の番号が公開の約束で、カーネルの実体は溝の中身で動かせます。 |
| 6 | `rcx` が像の範囲かを見る | 公開の像の `syscall` 命令へ、別の番号を `rax` に入れて跳べます。公開と内部の分割が飾りになります。 | 番号と溝を結びます。`rip == entry + 番号 × 16 + 10` を比べます。比較は一回です。 |
| 7 | 「システムのプログラム」の定義が無い | 三つが混ざります。OS と一緒に組まれた物、身元の級、置き場所です。`ls` は USER の級で動くシステムのプログラムです。第三者のプログラムは admin の身元で動けます。刻印は自己申告です。 | **置き場所で決めます。** `C:\Nocturne` の中は全部の溝です。そこはシステムしか書けません。身元の級と刻印は見ません。`C:\Programs` の付属のアプリも公開の溝だけです。 |
| 8 | 「OS が装置に合う module を決めて写す」 | 方針と仕組みが混ざります。カーネルが GPU の銘柄を知ることになります。一台に作り手の違う二つの GPU があると、一つの module では足りません（7600X にも内蔵の GPU があります）。 | カーネルは文書の handle から像を写すだけです。どの装置にどの像かは `services` の宣言の表 `gpu` の項目に足します。今そこが `nvrm` を選んでいます。選んで読むのはプログラムの中のローダーです。 |
| 9 | 差し込みと GPU を同じ「封じた module」にした | 必要が違います。GPU は OS のコードを速さのために入れます。差し込みは第三者のコードをプログラムへ入れます。 | 差し込みは対象から外します。今は別プロセスと channel で作れます。 |
| 10 | 「GPU が無い機械は llvmpipe の module」 | llvmpipe は Gallium の描画で、Vulkan のドライバーではありません。公開の口と合いません。Zink を通すと CPU の WebGL が今の直結より遅くなる見込みです。 | CPU の描画は機械ごとのコードではありません。今のままプログラムの中です。GPU が無い機械の Vulkan は装置なしと答えます。CPU の Vulkan（lavapipe）は後の項目です。 |
| 11 | 開く窓と保存の窓を「サービス」にした | `declared[]` のサービスは利用者 0 の身元で動きます（`user/apps/services.c`）。その窓で全部の利用者のファイルが見えてしまいます。 | 呼ぶ者の身元で動くシステムのプログラムにします。libc が子として起こし、channel で結果の完全なパスを受けます。`n_document_save` がパスで atomic に置き換えるので、handle にしません。OS の更新で全部のプログラムの窓が変わるのは同じです。 |

ほかに小さな直しがあります。

- 像の frame は `mm/program.c` を通しません。カーネルの中の物なので、今の時計の頁と同じ道で足ります。
- `proc_launch` は窓を出せません。カーネルは `N_ERR_WRONG_GENERATION` を返し、起こした側が言います。シェルの起動の失敗は既に通知で出ます。
- ファイルの窓は `C:\Programs` の外のプログラムを起こせません（監査の欠陥 16）。ここを直さないと、ポータブルは理由の窓にすら届きません。
- 位置の検査は `syscall_entry` のアセンブラでなく `syscall_dispatch` の頭で足ります。

## GPU の案の比べ

問いは一つです。**利用者側のドライバー（UMD）をどこに置くか。** 特権の半分 `nvrm` は既に別プロセスです。

| 案 | 中身 | 速さ | 新しい仕組み | 判定 |
|---|---|---|---|---|
| A 今のまま静的 | NVK がプログラムの中 | そのまま | 無い | 新しい GPU と修正が届きません。第三者のプログラムが出たら成り立ちません。 |
| B 全部を別プロセス | Mesa の Venus でコマンドを輪に流し、別プロセスが本物のドライバーで再生します。 | 落ちます。量は分かりません。 | 無い（channel と共有メモリーだけ） | **採りません。** 下に理由を書きます。 |
| C プロセスの中の像 | OS の持つ像を、作り手の表だけで呼びます。 | そのまま | 像を写す呼出し、スレッドの区画 | **採ります。** |
| D 上の一般の module | C を差し込みにも広げた形 | そのまま | C より多い | 必要が違う物を混ぜます。 |

**B は魅力があります。** プロセスの中に他のコードが入りません。ドライバーが落ちてもプログラムは残ります。PIC も TLS の設計も要りません。ローダーも要りません。元の報告は「往復 70 µs × 5,000 回で 350 ms」と書いて退けましたが、この計算は誤りです。Vulkan の記録は片道の輪に書くだけで、描画ごとの往復はありません。

**それでも採らない理由は速さです。**

- 手元で測れません。QEMU に実物の GPU はありません。
- 公開の値は一つで、条件が違います。Proxmox の開発者の SuperTuxKart は、ホストが 92 / 137 / 194 FPS、Venus の VM が 58 / 75 / 86 FPS でした（[pve-devel](https://lists.proxmox.com/pipermail/pve-devel/2025-November/076671.html)）。VM の費用を含むので、プロセス間の費用はこれより小さいはずです。どれだけ小さいかは分かりません。
- Collabora は、Venus の制限は同期にあると書き、ハードウェアに合わせたドライバーを手元で動かす vDRM は native の速さに届くと書いています（[Collabora](https://collabora.com/news-and-blog/blog/2025/01/15/the-state-of-gfx-virtualization-using-virglrenderer)）。vDRM の形は、今の NVK と `nvrm` の分け方と同じです。
- Mesa の文書は、Venus の renderer が `vkMapMemory` のために実装依存の動きに頼ると書いています。試されたドライバーの一覧に NVK はありません（[Venus](https://docs.mesa3d.org/drivers/venus.html)）。
- `AGENTS.md` は性能を試験の合格より先に置きます。測れない落ち幅を実機の唯一の道にはできません。

**C の前例があります。** Fuchsia は、アプリの中の `libvulkan` が `vulkan_loader` サービスから ICD の VMO を受けて読み込みます。ICD の出す記号は三つだけで、ABI の一部です。どの ICD かは GPU の装置が答えます（[RFC-0205](https://fuchsia.dev/fuchsia-src/contribute/governance/rfcs/0205_vulkan_loader)）。名前を探す道はありません。

**B に戻れる道は残ります。** プログラムが触るのは Vulkan の C の口だけです。隔離が要るプログラムのために、後からローダーの中で Venus の道を選べます。
