# カーネル描画改善（2026-10-14）

## 採用した変更

1. `WIN_DOUBLE_BUFFER`を明示した窓では、既存の二つの画素割当を提出用の二面として共有する。`SYS_WIN_MAP(fd, index, WIN_MAP_ACQUIRE)`で書ける面を取得し、`SYS_WIN_PRESENT`の最終引数へ`index+1`を渡す。提出時の画素コピーはない。Media Playerの全フレーム描画をこの経路へ移した。
2. 合成ジョブが全て終了した後、`EV_FRAME`で完了面と再利用可能な面を通知する。現在表示中の面は、次の提出が合成されるまで保持する。単に「読み終わった」から直ちに表示中の面を解放すると、移動・露出時にその面を再読できなくなる。通知は通常入力キューとは別の最新状態メールボックスで保持し、キュー満杯による消失を防ぐ。窓の非表示・画面外でも取得待ちが永久停止しないよう完了する。
3. 入力は周期待ちから直ちに起床して配送し、画素合成は周期まで損傷を蓄積する。`boot/limine.conf`の`wmrefresh=120`は依頼で提案された変更可能なVM方針。コード内に120Hzの固定上限はない。値0／設定なしは周期制御なし、正の値には恣意的な上限を設けない。待機APIがミリ秒単位なので120Hzは9msへ切り上げる（約111回/秒以下）。実モニターの垂直同期ではない。
4. 全矩形のRAM合成・窓参照を終えてから、VRAMへの転送中だけ`wm_lock`を解放する。転送が参照する`back`の再確保は完了待ちにする。ここでは窓の画素を参照していないため、窓の破棄・再確保・次の提出をVRAM転送から分離できる。
5. 自身の描画で必ず上書きするタイトル・枠・本文内部の影を省略した。丸角の透明部分には従来の全影パスを残す。RGB混合は赤・青を16bit間隔のレーンでまとめ、緑を別に処理する。255分母の丸めは従来と完全一致させ、256分母への近似はしない。メニュー項目、タスクバーボタン、時計等は損傷クリップと交差しない時に文字処理を省く。

## そのまま採用しなかった形と根拠

### BSPならスナップショット不要、という近道

`kernel/src/arch/smp.c`はユーザー実行用runnerをAPに設置し、`kernel/src/sys/sched.c`はユーザー実行をBSPとは独立に走らせる。`capture_layer`が高位カーネルaliasを読んでいても、同じ物理画素へのユーザー書込みは止まらない。したがって「合成がBSPなら同時更新されない」は成立しない。

さらに`SYS_WIN_PRESENT`の既存契約は指定矩形の提出時点のスナップショットである。ブラウザーは`win_update_rect`でツールバー、コンソール、動画パッチ、ページ損傷だけを公開する。共有面の直接読出しでは未提出の書込みまで表示され、提出矩形の境界を壊す。合成時までコピーを遅らせるだけでも同じ問題がある。新しい全フレーム契約を選んだクライアントだけでコピーを除去し、既存の保持型アプリを無断で二重バッファ化しない。通常ブラウザーの提出コピーは今回残している。

### `scene_first_layer`だけを条件にしたクライアント→VRAM直送

同関数が証明するのは、その損傷矩形について下位レイヤーを隠せることだけである。後続レイヤー、リサイズ枠、メニュー、音量パネル、通知、カーソルはその後の描画に残る。「矩形を覆うクライアントがある」から「画面上の全画素がそのクライアントだけ」とは推論できない。加えて`wm_remote_copy`と`SYS_SCREEN_GRAB`は`back.px`を読む。`remote_users==0`でも画面取得は利用可能なため、遠隔利用の有無だけでback更新を省くとローカルのスクリーンショットが古くなる。

これら全オーバーレイの非交差証明、クライアント座標と画面座標の分離、backの遅延実体化または整合した画面取得経路が揃えば直送自体には賛成する。しかし条件不足の直送は今回入れなかった。提出コピーを除く二重バッファでも、クライアント→back→VRAMの二回の転送は残る。

### `capture_scene`だけを根拠に合成全体のロックを外すこと

そのスナップショットは窓の幾何・タイトルを値で保持する一方、画素、wallpaper、出力backは借用ポインターである。窓のresize／destroyは画素を、`set_screen_size`はback・wall・検証用canvasを解放する。メニュー、タスクバー、カーソル等はライブWM状態も読む。したがって窓buf一つのrefcountだけでは全体の寿命・状態整合を解決しない。今回は安全境界が明確なVRAM転送だけをロック外へ移し、RAMラスタライズ中の所有権を維持した。ラスタライズ全体の解放は未実装。

## 利用契約と限界

- 二重バッファ利用者は毎回`win_begin_frame`から始め、全画素を描いて`win_update`する。提出後は取得完了までその面を書かない。既存の部分描画や同じcanvasの長期保持とは異なる契約。
- `win_update`後の`c.px`はNULLとし、誤って同じcanvasへ描き続けないようにした。rawの共有ポインターを保持して契約違反の書込みをするアプリまで、メモリ保護で禁止する実装ではない。
- `EV_FRAME`は合成の読取り完了・面の再利用通知であり、物理走査の完了ではない。垂直同期がないため実画面の走査中ティアリング消失は保証しない。
- 既存syscall番号、既存イベント番号、通常アプリの矩形提出、画面取得、RDPのRAM読取元は維持した。
- J-spaceはmedium、主担当のみ。参照マップは`.jspace/graphics-map.json`。他のチャット作成・サブエージェント・メモリ更新はしていない。

## 検証記録

速度向上率、全ブラウザーの互換性、長時間動画、音質、RDP同時接続、Hyper-V実機は今回の基本確認からは証明しない。

初期の二回はguestテストの配置を誤りコマンドを起動できず、正しい`/data/tests/*.c`をguestのtccでコンパイルする形へ訂正した。これらは不合格である。中間`wmverify`実行では元の影経路との画素一致と`wmramtest`が通ったが、合計観察時間内に後続40秒保持の終了通知が届かず、ハーネス全体は不合格。除外や期待値の変更で合格にしていない。

また、再ビルド完了前に起動した三台でinitrdが最終版と異なることをhash照合で検出した。専用ハーネスの停止要求で終了し、それらを最新版の証拠には使わない。ビルド完了後の`graphics-delivery-*`へ切り替えた。
