# カーネルのUnifont全字形対応

## 実装

- ユーザー提供の `unifont_jp-18.0.01.bdf` を採用。全57,086字形を収録し、256字形への限定・全角字形の縮小はしていない。
- 半角7,309字形は8×16、全角49,777字形は16×16。元の16行・全画素を保持。大サイズは描画時の厳密な2倍拡大。
- `common/unifont.bin` は65,536位置の幅表と32バイト/位置のビットマップ、合計2,162,688バイト。NASMで読み取り専用データとして埋め込む。
- 共有描画APIは32bitのUnicodeコードポイントを保持。カーネルコンソールは全角2セル、分割UTF-8、折返し・スクロール・後退・ANSI消去に対応。ウィンドウタイトルは画素幅とUTF-8文字境界で省略する。
- ユーザーUIのMaple Mono経路は維持。共有ライブラリーのビットマップfallbackも全字形表を使う。
- 原BDFは `third_party/unifont/` のgzip内にバイト単位で保存。原本SHA-256は `aa12991a14ddd06986832a57d37c25ffd46e3658ac04d56e253bc737448e8ada`。OFL本文・著作権表示・変換内容・出典も同梱し、起動イメージの `/usr/share/licenses/unifont/` に収録。

再生成と検査:

```text
python -X utf8 scripts/build.py bitmap-fonts
python -X utf8 tests/test_unifont.py
python -X utf8 scripts/build.py all
```

## 確認結果

- 原BDF全57,086字形について、元コードポイント・元幅・16行すべてを独立に照合し一致。未収録8,450位置は空で、原本・許諾SHA-256と再生成結果も一致。
- 実 `gfx.c` / `fbcon.c` のホスト試験は319,969,867画素・状態チェック、0失敗。これは画素単位の確認数であり、同数の独立利用シナリオを意味しない。
- 独立レビューでも原版との全字形照合を再実行。別のANSI・全角セル・WM省略検査410,473項目も0失敗。
- カーネル、全アプリ、IMG/VHD/ISO構築終了0。
- 最新媒体の隔離QEMU（WHPX・2GiB）で、1CPU/noguiコンソールと4CPUデスクトップを実行。日本語・中国語・ハングル・ギリシャ文字・キリル文字・記号を視認。日本語のタイトルと短いタイトルの省略も確認。
- 保存した実フレームバッファのコンソール6行とカーネルタイトル2本を元ビットマップと比較し、27,264画素チェック、0不一致。
- 既存ユーザーフォント試験は実ゲストで245項目、0失敗。
- 各ゲストの媒体内部kernel/initrdは検証時の最新buildとSHA-256一致。両QEMUは終了0・停止済み。ユーザーの永続dataディスクは接続していない。
- 初回35/40秒の試行は起動途中で期限に達したため成功に含めない。再試行では約50秒で表示・検査完了。

一次証拠は `build/kernel-unifont/` と `build/nocturne-platform/kernel-unifont-{console,gui}-02/` に保存。

## 境界

- 「全字形」は提供BDFに収録された全57,086字形。提供ファイルにはBMP外の字形がなく、未収録文字はU+FFFDになる。
- 複雑な文字整形、結合字形、端末の全角保存グリッド、メモ帳のUnicode編集まで完成したという意味ではない。
- コンソールの全角span表を確保できない低メモリ経路では、字形描画は続くが後退・上書きの追跡は保証しない。
- 可視ゲスト受入れは2GiB QEMUに限定。Hyper-V・実ハードウェア・512MiBでの完走は未確認。
