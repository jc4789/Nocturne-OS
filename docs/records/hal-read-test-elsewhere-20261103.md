## 結論

### 問い 1：Claude は正しく実装できるか

今の文書のままでは、できない。文書を直せば、大部分はできる。

- 文書のとおりに作ると壊れる所が三つある。
  - `struct pm_device` を消すと、USB ディスクの守りと「眠れない装置」の印が消える（R2）。
  - `hal_add` が `attach` を呼ぶと、`iommu_init` より先に割り込みが開く（R5）。
  - `vm_cpu.c` を製造者の一つにすると、VM の中で AMD の処理が走らない（R6）。
- 二人の Claude が別の物を作る所が四つある。
  - 網の輪の形（R7）。
  - 名前の持ち主（R8）。
  - `hal_lost` と再列挙の同期（R3）。
  - プロセスの実装の眠り（R2）。
- 動かして確かめられない範囲が、文書の書き方より広い。
  - S3 からの復帰は WHPX の QEMU で確かめられない（`.claude/skills/nocturne-project/references/qemu-visual.md:68`）。`quiesce` と `resume` は、この道具の範囲に入らない。
  - QEMU のフリップは即時で、帰線を待たない（`kernel/src/vm/vbe.c:80-84`）。フリップの鎖は実機でしか測れない。

### 問い 2：ほかの部分の手伝いを邪魔するか

HAL の骨組みは邪魔をしない。邪魔をするのは次の三つである。

- 入力、合成、網の道がプロセスの境目を越えること。呼出しの跡が切れ、計測の道具が無い。
- 今ある種類ごとの一覧と HAL の記録の関係が決まっていないこと。Claude は二つの一覧のどちらを直すか迷う。
- 手術が `pci.c`、`xhci.c`、全部のドライバー、`init.c`、`pm.c` に触れること。作業木の間、main の同じ場所の仕事がぶつかる。文書は作業木としか書いていない。

### 問い 3：一か月後も正しいと思うか

半分は思う。半分は思わない。

- 残ると思う：種類ごとの型のある契約、制御とデータの分離、関数の表を本物の継ぎ目に限ること、カーネルへコードを読み込まないこと。
- 後悔すると思う：下の R1〜R10。一番重いのは性能の関門（R1）と眠りの扱い（R2）である。

### 性能

HAL の部品は速い道に費用を足さない。`hal_device` を読む道は速い道に無く、`struct blkdev`、`struct audio_ring` は今のままである。これはコードと文書を照らして確かめた。

費用は全部「カーネルの外へ移す決定」から来る。文書の費用の表はその半分を載せていない（性能の節）。

## 範囲と証拠の限界

- 確かめたのはソースと文書だけである。ビルドも QEMU も動かしていない。実測の値はこの報告に無い。
- 数は二種類である。「計算」は周期と share からの算術である。「仮定」は仮定を同じ行に書く。
- `kernel/src/gui/wm.c`、`kernel/src/net/net.c`、`kernel/src/vm/rdp.c`、`ports/nvidia/display.c` は全部を読んでいない。要る所だけを読んだ。
- `docs/records/audit-*.md` の所見は、引くときに監査の番号を書く。行を自分で確かめた所は `file:line` を書く。
- FreeBSD は `rg` で二つの事実を確かめただけである（R3、R8）。設計の元にしていない。
- 所見の確信は「証明」（コードで閉じる）か「判断」（コードからの推論）で書く。

### 仕事 2：眠りの後に USB のキーボードが効かない

**読む順。**

1. `.claude/skills/nocturne-project/references/qemu-visual.md:68`。WHPX で S3 から戻れないことを先に知る。
2. `kernel/src/dev/pm.h:1-43` の文脈の決まり。`kernel/src/dev/pm.c` の `sleep_now`（347）と `machine_sleep`（287）。
3. `kernel/src/dev/usb.h:5-11`。`kernel/src/dev/xhci.c` の `xhci_resume`（2299）、`hc_worker`（2243）、`hc_restart`（2195）、`usb_remove`（1713）。
4. `kernel/src/dev/usbhid.c` の `usbhid_attach`（652）と `hid_report`（294）。
5. `kernel/src/dev/input.c` の `input_key`（126）。そこから窓のサービスへの輪。
6. 窓のサービスの輪の読み手。

**進め方。**

1. 報告の機械で本当に眠ったかを見る。今のコードでは、実機は S3 に入れない。
   - 表示に `resume` が無い（`kernel/src/dev/fb.c:629-636`）。
   - アプリのドライバーが居ると断る（`kernel/src/dev/pm.c:351-354`）。
   - USB ディスクがあると断る（`xhci.c:2311-2314`）。実機の媒体が USB なら必ず当たる。
   - 設計は三つのどれも変えない。だから「実機で眠った」報告は、設計の外の仕事が済んだ後か、VM の報告である。
2. serial のログで層を切る。行は `pm: going to sleep`、`pm: awake after`、`usb: controller N starting again after sleep`、`usb: vvvv:pppp class`、`usbhid: slot N interface M is a keyboard` である。
3. キーがカーネルまで来たかを見る。`struct n_power_events` の `last_input_ns`（`common/abi.h:744`）が動けば、`input_key` まで来ている。
4. 来ていれば窓のサービスを見る。来ていなければ `hc_restart` と再列挙を見る。
5. 再現は QEMU の S3 ではできない。休止なら同じ復帰の輪を通る（`pm.c:384`、`:327-334`）。休止の道で `xhci_resume` が走るかは、動かしていないので確かめていない。

**設計の後に増える疑い。**

- `hal_lost` の積まれた仕事と、新しい記録の `attach` の順序（R3）。
- 古い装置の `lost` が、新しい装置の押下の後に離しの事象を送る。今は `usbhid_detach`（`usbhid.c:574-576`）が worker の中で `usb_remove` の間に走るので、この順は起きない。
- カーネルの輪から窓のサービスのスレッドへの起こし。

### 仕事 3：窓を動かすと 1 フレーム遅れる

**読む順。**

1. 窓のサービスの主ループ。これは設計の後に現れるファイルである。
2. `kernel/src/dev/fb.h:143-171` のフレームの口と、設計の `SYS_SCREEN_*`。
3. `ports/nvidia/nvrm.c:94`（`irq_thread`）、`ports/nvidia/nvkms_os.c:576`（`q_thread`）、`ports/nvidia/display.c:1070`（帰線の知らせ）、`:1532`（`flip_thread`）。
4. `docs/records/audit-compositor-20261102.md` の T1〜T4、H6、H9、H10、F15。
5. `kernel/src/sys/thread.c:198-233` と `kernel/src/sys/sched.c:189-193`、`:466-478`。

**進め方。**

1. 何と何の差かを確かめる。ポインターと窓の差か、手と画面の差かで、層が変わる。
2. 同じ時計で一つの入力を追う。
   - `struct mouse_event.time_ns`（`kernel/src/dev/input.h:25`）は xHCI の drain の時刻である。
   - サービスが受けた時刻、`capture` の時刻、フリップを頼んだ時刻、`screen_flipped` の `time_ns` を並べる。
   - 時計はカーネルもプログラムも同じ monotonic なので、並べられる。
3. 位相を見る。今の形では、frame は表示の知らせの直後に始まり、damage をそこで切る（`wm.c:1433-1435`、`:1735`）。描いている間の動きは次へ回る。最低 1 周期の遅れはこの形から来る（T1）。
4. 鎖を見る。T3、T4、H9 の一周遅れの候補を、時刻の列で分ける。
5. ポインターを別の面で出す形に変わっていれば、窓がポインターから 1 コマ遅れて見える。今は絵に焼くので揃う（`docs/records/audit-compositor-20261102.md` の H6）。これは見込みで、設計の後の形が決まっていないので確かめられない。

**止まる所。**

- QEMU では帰線に関わる遅れを再現できない。`vbe_flip` はその場で `screen_flipped` を呼ぶ（`vbe.c:80-84`）。
- 実機の観測は USB のログと写真である。写真は 1 コマの差を写さない。ログを足すたびに媒体を組み直し、依頼者に起動してもらう。
- 落ちたコマの数を測る物が無い（F15）。先に作る。
- 受け渡しの形は `docs/hal.md:140` が「GPU と画面の手術で決める」と書く。文書を読んでも道が分からない。

## 一か月後に後悔しそうな決定（重い順）

### R1：合成と入力を移す費用を HAL の外へ出し、関門に数を置かない

- 決定：`docs/hal.md:140`、`:195`、`:197`、`:199-205`。
- 根拠：
  - 文書は性能を物差しに置く（`:15`）。一番重い道を「HAL でなく」と書いて外す（`:197`）。しかし画面と入力の契約はその道の形で決まる。
  - 関門に数が無い。「間に合わなければ」の相手が無い。依頼者の線は監査に書いてある（`audit-compositor-20261102.md:45-67`、280 Hz、600 Hz、1 ms、8000 Hz の入力）。
  - 三つの測りのうち二つは今の媒体で測れない。
    - フリップの鎖：`vbe_flip` は即時である（`vbe.c:80-84`）。
    - 網：`rtl8125` は QEMU に無く、QEMU は e1000 である（`.claude/skills/nocturne-project/SKILL.md:43`）。
    - `AGENTS.md` は「VM の測定値で実機の既定を決めない」と書く。
  - WHPX は PCID を見せない（`kernel/src/arch/cpu.c:7`）。アドレス空間を替える費用が実機と違う。
  - 切る前に測れるのは今の鎖だけである。新しい鎖はまだ無いので、測れない。
  - サービスの締切の上限が足りない。これは測らなくても計算で出る（下の表）。
- 起きること：手術の後で遅れが出たとき、戻す道も、形を変える根拠も無い。
- 確信：上限と即時のフリップは証明。遅れの量は測っていない。

アプリの締切のスレッドは、プロセスで合わせて一 CPU の半分までである（`kernel/src/sys/thread.c:198-233`、`:251`）。一つのスレッドの予約は `period × share` までになる（`kernel/src/sys/sched.c:189-193`）。カーネルのスレッドは周期の 15/16 までである（`sched.c:80`、`:190`）。

| 線 | 締切のスレッド | 周期 | サービスの予約の上限（計算） | 今の上限（計算） |
|---|---|---|---|---|
| 1440p 三枚の 280 Hz の画面 | 画面 3 + 入力 1 | 3.571 ms | 0.446 ms | 3.348 ms |
| 同じ、165 Hz の画面 | 同じ | 6.061 ms | 0.758 ms | 5.682 ms |
| 四枚目に 600 Hz を足す | 画面 4 + 入力 1 | 1.667 ms | 0.167 ms | 1.563 ms |

1440p の全面は 14.7 MB である。写しの速さを 20 GB/s と仮定すると（`audit-compositor-20261102.md:460` の仮定）、写しだけで 0.737 ms かかる。280 Hz の上限を超える。超えた分は fair 級で走る（`sched.c:466-478`）。全コアの負荷の下では y-cruncher と同じ級になる。

### R2：`struct pm_device` を `struct hal_driver` へ入れて消す。プロセスの実装の眠りを書かない

- 決定：`docs/hal.md:85-86`、`:59-68`。
- 根拠：
  - `resume` の `NULL` の意味が逆になる。今の `NULL` は「戻れないので眠らせない」である（`kernel/src/dev/pm.h:61`、`pm.c:248-253`）。文書の `NULL` は「要らない」である（`hal.md:85`）。
    - 今の表示、`tulip`、`virtio-gpu` は `NULL` で眠りを止めている（`fb.c:636`、`vm/tulip.c:115`、`vm/virtio_gpu.c:590`）。
    - 文書のとおりに作ると、実機で表示を戻せないのに S3 が出る。
  - `refuse` が消える。`xhci_refuse` は、USB ディスクがある間の眠りを断る。理由は「マウントしたファイルシステムの下に新しい装置として戻る」である（`xhci.c:2296-2298`、`:2311-2314`）。これが消えると C: を壊しうる。
  - `cold_ok` が消える。休止で firmware の表示を許す印である（`pm.h:64`、`fb.c:636`）。
  - 登録 11 件のうち `input` は装置でない（`kernel/src/dev/input.c:184`）。`display` は firmware の面と VM の画面をまとめた一つである（`fb.c:636-642`、`vm/vbe.c:219-224`）。`hal_driver` に置く先が無い。
  - プロセスの実装に眠りの道が無い。今は「アプリのドライバーには眠りを伝えていない」ので断る（`pm.c:351-354`）。文書の `quiesce` は割り込みを閉じた一つの CPU で走り、`resume` はほかのスレッドが走らない所で走る（`pm.h:28-40`）。プロセスはそこに入れない。
    - 実機で表示のモードを戻せるのは `nvrm` だけである（`fb.c:630-632`）。つまり GPU のある実機の S3 は、この欠けた道でしか成り立たない。
- 起きること：依頼者の機械で眠りが動かないまま HAL が終わる。次に足すとき、`hal_driver` の形から直す。
- 確信：証明。

### R3：`hal_lost` は「どの文脈からでも」「仕事を積む」。USB の interface を子の記録にする

- 決定：`docs/hal.md:50`、`:78`、`:212`。
- 根拠：
  - USB の順序は同期に頼っている。`hc_restart` は全部の `usb_remove` が終わってから `hc_start` する（`xhci.c:2209-2224`）。`usb_remove` は class の detach が終わってから slot を返す（`:1730-1734`）。積むだけの `hal_lost` では、待つ口が要る。三つの操作に無い。
  - `dev/usb.h:5-6` は attach、detach、work が「その controller の worker で、一度に一つ」と決めている。別の糸で `lost` を呼ぶと、この決まりが消える。class のドライバーは全部これに頼る。
  - 構成を選ぶ前に、ドライバーの有無を聞く（`xhci.c:1446-1456`、`:1461`）。記録を作る前に引く口が要る。三つの操作に無い。
  - CDC の網は二つの interface を一つのドライバーが持つ（`usbnet.c:33`、`:217-232`）。FreeBSD も同じ形で親の interface を印す（`sys/dev/usb/net/if_cdce.c:647`、`usbd_set_parent_iface`）。一致の表は interface 一つごとに引くので、二つ目の持ち方が要る。
  - 木を割り込みを閉じて歩く問題がある。今の段の一覧は伸びるだけで、錠なしで読む（`pm.c:37-38`）。理由は、CPU を止めた後に錠を待てないこと、電源を切るときは別の CPU が動いていること（`pm.h:30-32`）である。`hal_lost` で変わる木は、この歩き方を許さない。
  - 「状態の書き手を `hal.c` の一つにする」（`:212`）は、この競合の設計になっていない。速い道の `usb_device.removed`（`usb.h:102`）と `blkdev.gone` は残る。
- 起きること：USB の 4293 行（`xhci.c`、`usbhub.c`、`usbhid.c`、`usbmsc.c`、`usbnet.c`）の書き直しが、動かして確かめられない順序に頼る。S3 は WHPX で試せない。
- 確信：順序の依存は証明。書き直しの量は見積っていない。

### R7：網の「共有の輪」の形を決めない

## 設計が見落としている、OS に要るもの

1. **プロセスの実装の眠り。** 伝える段、答えを待つ期限、断る口。R2。
2. **眠りの守り。** 戻れない装置、断る装置、冷たい起動でだけ戻る装置の印。R2。
3. **起動をまたぐ鍵。** バスが作る。今の四つの鍵と同じ物にする。R8。
4. **バスの種類。** ACPI（電源ボタン、蓋、これから EC と電池）、固定のポート、VMBus の GUID。R5。ノート PC の内蔵キーボードの i8042 と I2C の HID は今の `dev/` に無い（`rg` で 0 件）。入力の表の外である。
5. **電源の契約。** `architecture.md:40` は「電源と温度」を挙げる。表は温度を先送りし、電源を書かない。`pm.c`、`power.c`、`acpi.c` の置き場が無い。
6. **失敗の状態。** `attach` の失敗の状態と理由。F15（失敗しても RUNNING）を別の形で繰り返す。
7. **`n_hal_publish` の寿命と権限。** どの能力で作るか。`nvrm` が死ぬと記録はどうなるか。`n_hal_*` を誰が読めるか。文書は一行しか書かない（`hal.md:133`）。
8. **錠の順。** 木の錠の種類（spinlock か mutex か）と、`.claude/rules/kernel.md` の順のどこに入るか。`attach` は眠り、`hal_lost` は割り込みから呼ばれ、`quiesce` は割り込みを閉じて歩く。
9. **PCI の `lost` の出どころ。** PCI に抜き差しも AER も無い（K5）。文書の `lost` は USB と VMBus にしか来ない。NVMe が消えた機械、GPU がバスから落ちた機械の道が無い。
10. **場所の情報。** `hal_identity` にセグメントも NUMA の node も無い。`pci_device.node` はある（`pci.h:19`）。輪とサービスのスレッドを装置の近くへ置くのに要る。PCI のセグメント 0 の限定は既知の欠陥である（`open.md`）。
11. **窓のサービスが落ちたとき。** 文書の「落ちたとき」はプロセスの実装だけを書く。入力の持ち主が居ない間の道は `init.c:56` の console しか無い。
12. **`fb_hold` と直接の緩衝。** `nvrm` が BAR を切り替える間、書込みを止める口である（`fb.h:38-45`）。サービスが緩衝へ直接書くと（`hal.md:108`）、カーネルは止められない。取り上げる口が要る。
13. **画面の記録の単位。** 接続口かモニターかが無い。今の `struct screen` は消えない（`fb.h:59-60`）。`HAL_LOST` と合わない。
14. **`scanout_*` の後継。** 性能の節に書く。

## 代わりの形

短く書く。どれも `docs/hal.md` の直しで済む。

1. **関門に数を置く。** 同じ機械で、今のカーネルの合成と比べる。入力から表示までの時間が悪くならないこと、全コアの負荷で落ちるコマが 0 であること。測る場所は実機とする。落ちたコマの数え方を先に作る（F15）。
2. **窓のサービスの級を決める。** 能力で share の制限を外す。`nvrm` の糸を同じ級にする。これは手術の前に決められる。
3. **試作を換える。** 一つ目は USB の木と `lost`（QEMU の `usb-kbd`、`usb-tablet`、USB ディスク、抜き差し、休止の道）。二つ目は `desktop` と合成のスレッドだけをプロセスへ移して実機で測る。画面の種類はその後にする。
4. **眠りの宣言。** `enum hal_sleep { 何もしない, 戻れない, 冷たい起動でだけ戻る, 呼出しで戻す }` と `refuse` を `hal_driver` に置く。装置でない `input` は `woke` の事象を聞く。プロセスの実装には、`smp_suspend` より前のスレッドが動く段で伝える。
5. **`lost` は親のバスの worker で走らせる。** どの文脈からでも呼べるのは、印を立てて worker を起こす所までにする。USB は今の `hc_worker` のままで、`usb.h` の決まりが残る。木の歩きは眠りの前に変更を止めて行う。
6. **`hal_add` を二段にする。** 列挙は記録だけを作る。`init.c` が `iommu_init` の後に `hal_bind_all` を呼ぶ。後から来た物はその場で結ぶ。
7. **身元を型で分ける。** `pci`、`usb`、`vmbus`（GUID）、`acpi`（`_HID`）、`platform` の union にする。安定した鍵と NUMA の node は記録の欄にする。
8. **USB に二つの口を足す。** 構成を選ぶ前に聞く `hal_can_bind` と、二つ目の interface を持つ `hal_claim_sibling`。
9. **CPU の製造者は二つにする。** AMD と Intel。VM の差は TSC の速さだけで、`vm_tsc_stated` を `vm/vm.h` に置く。
10. **名前は記録に置く。** 長さを決めず、バスかドライバーが埋める。機種の表が要るときは、プログラムの側で読む。サービスは作らない。種類ごとの一覧は記録の id と鍵を持つ。
11. **網の輪はソフトの輪と書く。** 輪の数は申告にする。装置の記述子はカーネルだけが書く。写しの費用を測って、足りなければ IOMMU の領域と一緒に変える。
