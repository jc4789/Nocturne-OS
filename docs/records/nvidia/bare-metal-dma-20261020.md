# NVIDIA 実機の初期化停止と DMA 境界修正

## 結論と対象

提供された写真7枚をすべて目視し、615.78.08のRM、NocturneのPCI・DMA・メモリ型処理と照合した。
**SEC2 FalconのスクラバーIMEM転送が完了しないことは確認できるが、その実機上の原因は
確定していない。今回の境界修正を実機復旧とは扱わない。**

残っていたブラウザーの変更は対象外として保全した。作業中、今回のOS層修正とホスト試験が
`783706b0` としてコミットされた。こちらからコミット・履歴操作はしていない。

## 写真から確認した内容

| 写真 | 確認した内容 |
|---|---|
| 1 | `10de:2786`、`01:00.0`、RM 615.78.08、能力登録 `0x56`、BAR情報、両ファームウェアの読込み |
| 2 | 同じ起動経路、9秒・30秒でも初期化中、処理割り込み0件 |
| 3 | Ryzen 5 7600X、12論理CPU、約30GiBの利用可能RAM、PAT値、フレームバッファーの物理範囲 |
| 4 | 横に切れた行の右端を含むFalcon DMA失敗、`kernel_gsp_falcon_ga102.c:242`、`kernel_gsp_tu102.c:406` |
| 5 | 最初の2回のスクラバー失敗と、その間も続く初期化経過表示 |
| 6 | 180秒付近までの3回の同じ失敗 |
| 7 | `mode: 1`、`0x00000065`、IMEM引数、複数の表明が同じエラーを伝播していること |

写真は起動した版の証拠であり、後から変更したコードの動作証拠ではない。
`/data` が永続化されていないことも写真にある。RAMディスクのログ提出は要求していない。

## 値と失敗箇所の解釈

- **`0x56` は `NV_ERR_NOT_SUPPORTED`。** `nvidia_caps_root == NULL` のため
  `osRmCapRegisterSys` が未対応を返す。`_sysCreateOs` はここを非致命的な失敗として扱い、
  `NV_OK` を返して続行する。PCI Commandの値でも、DMAエラーでもない。
  能力管理を実装せず成功だけ返す変更や、ログを隠す変更はしない。
- **`0x65` は `NV_ERR_TIMEOUT`。** 数値はNVIDIAのソフトウェア状態コードで、
  FalconのDMAレジスターをそのまま表示したものではない。
- **`mode: 1` は `FLCN_DMA_POLL_ENGINE_IDLE`。** `DMATRFCMD.IDLE` のビット1が
  立つのを待つ経路。モード0のキュー空き待ちとは異なる。
- Adaの `kgspExecuteScrubberIfNeeded_AD102` は **SEC2** のFalconをリセットし、
  `kgspExecuteHsFalcon_GA102` でスクラバーを読み込む。写真の242行はIMEM転送の戻り値検査。
  その後のDMEM転送・署名設定・Falcon CPU起動にはまだ進んでいない。
  従って、この記録だけを署名不一致、GSP実行中の異常、MSI故障と断定しない。
- 転送コマンドは定義から `0x614` と計算できる：
  `SIZE=6 << 8`（256バイト）、`IMEM=1 << 4`、`SEC=1 << 2`、
  `WRITE=0`、`CTXDMA=0`。**これはコードから導いた書込み値であり、実機での読戻し値ではない。**
  DMA基底は256バイト単位で、低32ビットと上位9ビットに分ける既存処理に対応する。
- 表示の `4000 msecs` は `threadStateDatabaseTimeoutMsecs`。
  実際のデバイス初期化では `_threadNodeInitTime` が少なくとも60000msへ拡張する。
  約60秒おきの失敗を、これだけでNocturneの時計が15倍遅い証拠とはしない。
  時計・期限の引延ばしは行っていない。

根拠は同版の `nvstatuscodes.h`、`falcon_common.h`、
`kernel_gsp_falcon_ga102.c`、`kernel_gsp_ad102.c`、`thread_state.c`、
`src/nvidia/arch/nvalloc/unix/src/os.c` と `src/nvidia/src/kernel/core/system.c`。
使用中のエラー定義、Falconレジスター定義、転送、Adaスクラバー、時限、systemの6ファイルは、
指定されたローカルの615.78.08ともSHA-256で一致した。

## アドレスと PCI の境界

- BAR0：`0xfb000000`、長さ `0x1000000`（16MiB）。
- BAR1：`0xf800000000`、長さ `0x400000000`（16GiB）。
  BARの窓の大きさであり、この値だけで実VRAM容量を断定しない。
- 起動画面：`0xf800000000` から `0xf800870000`。
  `8192 × 1080 = 0x870000` で写真のpitch・高さと一致し、BAR1の先頭にある。
- `0x0x600000085000` はRMの `0x%p` とNocturneの `%p` の接頭辞が重複した表示。
  この文字列だけからページテーブルの破損とは判断できない。
- PAT `0007010600070406` の索引3はUC、索引5はWC。
  Nocturneの共有マッピングが選ぶ索引とは一致する。ただし、実機の全別名写像や
  TLB・キャッシュ状態が正しいことまで写真で証明できるわけではない。

PCI Commandはオフセット `0x04` の16ビットレジスターで、MSEはビット1、BMEはビット2。
NVIDIA公開の `manuals/ampere/ga102/dev_nv_xve3g_fn0.ref.txt` の定義とも一致する。
その値は提供写真にない。BARのCPU側写像成功からBMEを推定してはいけない。
また、Nocturneが物理アドレスをDMA先として返すことと、ファームウェア側でIOMMUが
通過状態になっていることは別である。今回、IOMMU状態を確定したとは報告しない。

PCI Commandの意味については
[Intelの公開レジスター資料](https://edc.intel.com/content/www/us/en/design/publications/core-processors-series-3-cfg-and-mem-registers/001/pci-command-pcicmd-offset-4/)
も照合した。Intel固有の初期値をAMD実機の値として使用していない。

## 実装した範囲

`ports/nvidia/os_pci.c` の既存責務内で修正した。

1. 非連続DMA割当の最後のページだけでなく、全ページの到達可能範囲を検査する。
   連続割当では全長を検査し、末尾アドレスの加算オーバーフローを避ける。
2. 実際のDMAマスク、DMA32要求、OSの4KiBページ境界を使用する。
   4GiB以上の正当な割当を一律に禁止しない。
3. 大ページ整列の入力と余分な割当のサイズを検査し、失敗時に元割当・整列用view・
   アドレス表を同じ所有権経路で解放する。
4. CPU／クライアントのマッピングとviewで、丸めの前に要求全体を実割当範囲と照合する。
   巨大な長さの桁あふれを、小さい有効範囲と誤認しない。
5. PCI Commandを読取り専用で表示する。BMEを書き換えず、未検証のIOMMU状態を明記する。

これらはコード上の境界・失敗時処理の不備である。写真のスクラバーは連続割当を使うので、
非連続ページの検査修正を今回の実機タイムアウト原因の修理と取り違えてはいけない。

## 検証と残件

- 実コードを含む `tests/nvrm_dma_hosttest.c` で、範囲・整列・失敗時解放・写像を検査。
  ネイティブサービスはモックであり、PCI、IOMMU、CPUキャッシュ、GPUの動作は証明しない。
  最終結果は失敗0件。追加したフラグ検査の初回は、DMA32期待値を通常の広域DMAの事例へ
  誤配置して1件失敗した。通常事例とDMA32強制事例を分けて訂正し、両方を検査した。
- `python -X utf8 scripts/build.py -j 4 --log build/nvrm-20261020-compile.log build/nvrm/os/os_pci.o`
  は成功。変更した製品用OS層の1オブジェクトだけをコンパイルした。
- `all` の実行予定にはNVIDIA以外の広範な再コンパイルが含まれたため、全体ビルドは実行していない。
  リンク・initrd・IMG・VHD・VHDX・ISOは今回未更新。既存媒体を修正入りとは扱わない。
- QEMU・Hyper-V・実機試験は実施していない。VM起動や永続データ操作もしていない。
- 主残件は、実機でのDMA完了停止と安全な表示引継ぎの解決。実機状態の裏付けなしに
  BME、BAR、IOMMU、リセット制御へ追加の書込みを行う修正は入れていない。

ローカル資料では `open-gpu-doc` のレジスター定義・Falcon説明と、
`open-gpu-kernel-modules-615.78.08/src` のOS非依存部分を使用した。
NVAPI、go-nvml、go-nvlibは既存ドライバー上のAPI／ラッパーであり、
この初期化停止を解決するための代替ドライバー実装として取り込んでいない。
Linux固有層や他OSのソースは参照・取り込みしていない。
