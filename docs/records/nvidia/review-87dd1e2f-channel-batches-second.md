# native channel・event 消費の追補第二検討

第一検討の「複数 wait にすれば成功してよい」という結論を、偽の成功を作る反例で再検討した。

- event queue は level-triggered なので、受信しなければ同じ ready handle が次にも返る。
  そのため batch を受け取った直後に本文を受信して消費する。戻り件数の単純な累計だけでは成功にしない。
- token は配列 index に用いる前に範囲を検査し、既に見た token は失敗にする。
  最終96個の一意な範囲内 token は、96接続すべてを覆うことを意味する。
- 各 token に対応する本文値と送信主体も必須なので、別 connection の event/本文が入れ替わっても検出する。
  RECEIVEABLE が無い event、途中0または負値、出力容量超過も失敗する。
- 一回の戻り件数を96とする条件だけは、明記された既存バッチ契約に反するため訂正する。
  元の235検査/1失敗と、その文書・実装根拠は第一追補へ保持した。製品を試験へ合わせた変更はしない。

未変更の同じ試験を反復するのではなく、契約誤読を修理したこの source を親が再配置して実行する。
担当自身は VM を操作していない。NVIDIA 実機、Hyper-V、性能、任意 OOM は未確認のまま区別する。
