# Nocturne の核の芯：立場 A「芯を薄く」

2026-10-31。紙だけの設計。照らしたのはコードとハードウェアの仕様（PPR 56713・55898、SOG 57647、AMD-Vi 48882、xHCI、NVMe 2.4、APM vol.2）。どの OS のカーネルのソースも読んでいない。

## 1. 要旨

1. 核は隔離の機構（番地空間、能力、物理の頁の持ち主、IOMMU）と期限の機構（時刻、CPU の配り、割り込みの届け）だけを持つ。装置のドライバー・格納庫・網・窓と合成・nvrm は、それぞれ別の主体で動く。
2. 毎コマ・毎事象の道は「持ち主は制御を持ち、道は貸す」で通す。持ち主の主体が、装置の待ち行列・事象の輪・走査の面を共有の記憶として使い手へ貸す。核が渡すのは、割り込みの届けと「register 一つへ書く権利」だけ。だから主体の境界をまたぐのは、操作ごとではなく束ごと・コマごとになる。
3. CPU は「席」と「急ぎ」の二つで配る。席は、量の仕事を CPU の空間で分ける。急ぎは、画面・音・入力の周期に結んだ予約を、CPU ごとに期限の早い順で走らせる。7600X には PCID が無く、主体を切り替えるたびに TLB が消える。だから、違う主体の間を時間で細かく刻まない形にするしかない。
4. 合成は GPU で行い、全画面のゲームは直接の走査にする。各画面の締めに核の期限を結ぶ。合成の CPU は 1 コマ 120〜250 µs、入力は 125 µs ごとに束で届く。同時の重さのとき、系の仕事の合計は機械の約 2%。
5. どこまで別の空間に出すかは、第 0 段の実機の測りで決める。測るのは、空間の往復の費用、割り込みから thread が走るまでの遅れ、8000 Hz の入力と飽和した NVMe での CPU の割合。閾値を越えた道は、主体を「合わせて」直す。核へは戻さない。

## 2. 物差しの時間の予算

「締め」は、その画面の次のコマのために、合成の主体が最新の入力とアプリの絵を取る時刻。三枚のうち真ん中の画面は、依頼に無いので 240 Hz と仮に置く。単位は µs。

| 画面 | 1 コマ | 締め→帰線 | 合成の CPU | GPU の合成 | flip と余白 | アプリに残る |
|---|---|---|---|---|---|---|
| 1440p 280 Hz | 3571 | 1100 | 200 | 500 | 400 | 2471 |
| 1440p 240 Hz | 4167 | 1200 | 200 | 550 | 450 | 2967 |
| 1440p 165 Hz | 6061 | 1500 | 250 | 700 | 550 | 4561 |
| 1080p 600 Hz | 1667 | 600 | 120 | 250 | 230 | 1067 |

- **GPU の合成**：4 層を読み 1 枚を書くと約 74 MB。実効 300 GB/s なら約 250 µs。表の残りは、ゲームの GPU の仕事を横取りして入るまでの待ち（未確認、8 に書く）。全画面のゲームは直接の走査なので、合成するのは cursor の面だけ（CPU 約 50 µs、GPU 0）。
- **入力（8000 Hz）**
  - USB の運びの 125 µs は装置の事実で、我々の分ではない。
  - xHCI の割り込みの抑え IMODI は 400 にする（250 ns 単位で 100 µs、xHCI §5.5.2.2）。既定は 4000（1 ms）なので必ず変える。これで報告ごとに割り込みが来る。
  - 核の分（割り込み→知らせ→急ぎの thread が走る）は、起きている CPU で 10 µs 以内。眠っている CPU では、これに眠りの出口が足される（深さは次の期限で選ぶ、5.2）。
  - 読む側の処理は 10 µs。
- **同時の重さ**：ゲームは 280 Hz の画面で直接の走査、動画は 240 Hz、SNS は 165 Hz。系の CPU は 1 秒あたり次のとおり（機械は 1 秒に 12 CPU 秒）。

| 仕事 | 量 |
|---|---|
| 合成（2 面＋cursor） | 240×200＋165×250＋280×50 ≈ 100 ms |
| 入力（一回 3 µs＋主体の切り替え 2 回、各 2 µs と仮定） | 8000×7 ≈ 56 ms |
| nvrm の flip（3 面） | 685×20 ≈ 14 ms |
| 音（周期 2.67 ms、一回 50 µs） | ≈ 19 ms |
| 核（配り・割り込み・期限） | 50 ms 未満（推定） |
| 計 | 約 0.24 CPU 秒（機械の 2%） |

落ちるコマを 0 にするのは、この 2% の小ささではない。決め手は二つある。ゲームの描画の thread と合成に急ぎの予約が入っていること（5.1）と、GPU 側の優先（8）。

NVMe を飽和させても画面が固まらない理由も同じ形にある。窓の主体は、毎コマの道で格納庫を待たない（絵と字体は前もって読む）。核は I/O をまたいで錠を持たない。

## 3. 脅威の模型

| 相手 | 狙い | 守り |
|---|---|---|
| 悪意のアプリ（入れた・移植した） | 他のデータと鍵、画面の盗み見、入力の盗み、昇格、他の画面のコマを落とす、記憶を奪う | 主体の境界。能力でしか届かない（大域の名前は格納庫の主体が判断）。画面と入力は窓の主体だけが配る。予約と口座 |
| 壊れたアプリ | 落ち・暴走 | 同上。予約を超えた分は自分の量へ落ちる |
| 外から来たコード（頁の JS・Wasm、媒体のファイル、TLS の相手） | ブラウザーの主体を乗っ取る | ブラウザーの中の区画（別の番地空間、能力はほぼ無し）。PKU は CFI のある所の補いだけ |
| 壊れた・悪意のドライバー（RM は大きい） | 全記憶、他の装置 | 主体の境界。IOMMU の領域には自分の DMA の物だけ。割り込みは装置ごとの付け替えの表だけ（48882 の装置表の IntCtl と表の根）。MMIO は自分の BAR だけ |
| 装置の DMA（悪意の装置、USB4 のトンネル、firmware） | 記憶の読み書き | 起動から既定で全部を拒む IOMMU |
| 網の相手 | packet の解き手の穴 | 網の主体。乗っ取られても核と格納庫には届かない |
| 盗まれた機械 | 置かれたデータ | 格納庫の暗号化と fTPM の封印、起動の鎖（未設計、9） |

範囲の外：SMM と firmware（AMD-Vi は SMI を止められない）、走っている機械への物理の攻撃。SMT の兄弟の間の横の道には STIBP を常に入れる。信じない主体を兄弟に同時に置かないかどうかは 9 で決める。

**正直な点：TCB は核だけではない。**
- 次のものも入る：見守り（全権の最初の持ち主）、母線の主体（ACS を切れば隔離が崩れる）、ACPI の主体（AML は任意の口と番地に触れる）、起動の鎖。
- 格納庫は全データを持ち、窓の主体は全画面と全入力を持つ。だから秘密については、この二つも TCB に入る。
- 薄い核が下げるのは「一つの誤りで全体が落ちる」率で、秘密を守る TCB の大きさではない。

## 4. 空間と境界の配置

| 空間 | 中身 | 持つ能力 | 区画 |
|---|---|---|---|
| 核（ring 0） | 強制の核 | すべて | — |
| 見守り | 起動の順、再起動の方針、主体の作成 | 最初に全部を受けて配る | — |
| 母線 | PCI の列挙・資源・ACS・FLR・hotplug | ECAM | — |
| ACPI | uACPI（AML）、装置の電源の手順、眠りの値 | ACPI の領域と口 | — |
| 記録 | 輪を読み、serial・画面・C: へ出す | UART | — |
| ドライバー（NVMe・AHCI、xHCI＋USB、HDA、NIC） | 一つの機能に一つの主体 | その機能の BAR・DMA・割り込みの源 | USB の型ごと（HID・MSC・網） |
| 格納庫 | `common/store`＋今の `fs/` | NVMe から借りた I/O の待ち行列 | — |
| 網 | TCP/IP・DHCP・DNS | NIC の輪 | 名前の解き |
| 窓と合成 | 窓、合成、入力の行き先、cursor、モード | nvrm からの GPU の channel、入力の輪 | — |
| nvrm | RM＋NVKMS | GPU の機能 | — |
| アプリ | | 起動で渡された能力だけ | アプリが作る |
| 外から来たコード | 頁、Worker、媒体の解き、webfetch | 自分の輪と共有の絵だけ | 区画そのもの |

**二つの境界**
- 主体の境界：身元・口座・能力の表がすべて別。
- 区画の境界：身元と口座は同じで、番地空間と狭い能力の表だけが別。身元を作らないので、作るのは安い。

**境界と直交する方針**

| 方針 | 持ち主と形 |
|---|---|
| IOMMU | 機能ごとの領域。群は母線の主体が決め、核が書く |
| GPU の文脈 | nvrm が、アプリごとの GPU の番地空間で |
| 予約の群（CPU・記憶・帯域・L3） | 配りの係 |
| 再起動の単位 | 見守りの方針 |
| 身元 | 主体の番号。主 thread の番号とは別で、2^31 まで使い回さない（今の ABI のまま） |
| UI と入力の権限 | 窓の主体 |
| 起動の信頼 | Limine が載せる束を、核が一度だけ確かめる |
| 秘密 | 後で作る鍵の主体 |

**道の貸し**：この立場で速さの規則を満たす芯。

- **入力**
  - xHCI は interrupter を複数持ち、TRB の Interrupter Target で事象の輪を選べる（xHCI §4.17）。
  - マウスを二つ目の interrupter に向け、その事象の輪と MSI-X を窓の主体へ貸す。全画面のゲームには、窓の主体の許しで同じ輪を読ませる。系の鍵の組合せは、窓の主体も同じ輪で見る。
  - xHCI の主体は transfer の輪を前もって長く積み、束で足すだけ。
- **格納**
  - NVMe の I/O の待ち行列の対を、CPU ごとに格納庫の主体へ貸す。
  - doorbell は、CAP.DSTRD が 0 なら 4 byte 間隔で同じ頁に並ぶ（NVMe 2.4 の CAP 35:32）。だから頁で写して渡せない。核は「この register に書く権利」を能力として渡す（syscall 一回、空間の切り替えは無い）。
  - 管理の待ち行列・初期化・reset は NVMe の主体に残る。
- **画面**
  - 全画面のアプリは直接の走査（今の `win_direct`）。
  - 合成の主体は、GPU の channel に利用者の doorbell で投げる（ports/nvidia の NVK が既にこの順で投げている）。

## 5. 芯の部品

### 5.1 CPU の時間の配り（席と急ぎ）

**何のため**：締めの期限、入力、ゲーム、何日も続く y-cruncher を同時に満たす。

**形はどこから来たか**
- (a) 7600X（Model 61h）は PCID が Fixed,0（PPR 56713 の CPUID 1 ECX）。CR3 を書くたびに、G でない TLB の項目が消える。違う主体へ移るときは IBPB も払う。だから、違う主体を同じ CPU で細かく刻むのは高く、同じ主体の thread どうしを刻むのは安い。
- (b) 画面ごとに周期と期限が違い、1 コマの仕事には上限がある。これは実時間の理論の「予算つきの期限」と同じ形になる。一つの CPU では期限の早い順が最適で、間に合うかは利用率の和で判定できる（数学の事実）。似ていることはここに書いておく。
- 捨てた「実時間の級＋周期 10 ms・予算 8 ms」との違いは三つ。周期は装置から来る。優先は数ではなく期限。受け入れの判定がある。

**作り：席**
- 各 CPU に「量の仕事の順」を置く。順は、持ち主の群、次に貸す群の並び。
- 持ち主の群に走れる thread が無ければ、次の群がすぐ走る（CPU を遊ばせない）。持ち主の thread が走れるようになれば、貸しをすぐ止める。
- 群の中は、同じ長さの時間で順に回す。期限を立てるのは、走れる thread が 2 以上ある席だけ（周期の拍は無い）。
- 席の数は配りの係が決める。配りの係は利用者の主体で、node ごとに thread を持つ。群の重みと使った量から、群の変化の事象をきっかけに決め直す。決め直しの間には下限を置き、見回りはしない。

**作り：急ぎ**
- 予約は（周期、予算、期限）の三つ。周期は、画面の帰線・音の周期・報告の間隔から来る。
- 受け入れのときに CPU を一つ決め、その CPU の急ぎの利用率の和を 0.6 以下に保つ。残りは量の仕事と核の分。
- 予算を使い切った thread は、次の周期まで自分の群の量の仕事へ落ちる。
- 入らない予約は「断り」として返し、黙って薄めない。
- 焦点の窓の持ち主には、窓の主体がその画面の周期の予約を渡す。UI の権限と予約の群が交わる所。

**数字**
- 急ぎの合計（例）：
  - 合成の 3 面で一つの CPU の約 15%
  - 入力 4%（予算 5 µs／125 µs）
  - 音 2%
  - ゲームの描画の thread 42%（例：1.5 ms／3.57 ms）
- 合わせて 0.63 CPU を 2〜3 の CPU に配る。
- y-cruncher だけが走るときは、12 席すべてが y-cruncher のもの。thread は席から動かないので、キャッシュ・TLB・node の記憶が近いまま。失うのは、急ぎが来る CPU での数 % と、TLB の入れ直しの分（第 0 段で測る）。

**1024 CPU と NUMA**：大域の実行の列は無い。席の順も急ぎの列も CPU ごと。配りの係は node ごとで、node の間の均しはもっと遅い間隔で行う。起こしの IPI は目当ての CPU にだけ送る。

### 5.2 時刻と期限

**何のため**：締め、予約の周期、利用者の timer、眠り。

**形はどこから来たか**
- 不変の TSC は P0 の速さで進み、P 状態でも C 状態でも変わらない（PPR §2.1.9）。
- LAPIC の timer は 2×CLKIN で数え、刻みは 1〜8。ARAT が Fixed,1 なので、深い眠りの間も動く。
- TSC-deadline は CPUID 1 ECX の bit 24 が予約になっていて（PPR 56713）、7600X には無い。
- だから起こしの装置は LAPIC の one-shot 一つで足り、起こしの装置の抽象（捨てた形）は要らない。Hyper-V も QEMU も LAPIC の timer を見せる。

**作り**
- CPU ごとに期限の列を持つ（TSC の値の順に並べた heap）。一番早いものだけを one-shot の数に換えて書く。
- 利用者の timer は幅のある期限（いつからいつまでに起きればよいか）にし、重なる起こしを一つにまとめる。
- 時刻は、利用者が RDTSC と読み取り専用の時刻の頁で読む。頁には速さと基点を置き、二つの版を交互に書く。syscall は要らない。
- 速さの直しは今の考え（P0 の FID・DID から始め、HPET を参照に直し続ける）を引き継ぐ。
- 眠りの深さは、その CPU の次の期限までの間と、ACPI が示す出口の遅れから選ぶ。

**数字**：one-shot の誤差は、40 ns の刻みと換算を合わせて 1 µs 未満。

**1024 CPU と NUMA**：列は CPU ごと。thread が別の CPU へ移っても timer は元の CPU で鳴り、目当ての CPU へ知らせる。2 ソケットの TSC が揃っているかは起動時に比べる。

### 5.3 割り込みと装置の事象

**何のため**：装置の事象を、他を乱さずにその持ち主の主体へ届ける。

**形はどこから来たか**
- ドライバーは別の番地空間にいるので、その code は主体の thread としてしか走れない。だから核の仕事は EOI・知らせの bit・起こしの三つで終わる。
- 外から見た「割り込み→thread」の形は、捨てた形に似る。違いは、核の中に二段目の処理が無いこと。この形を強いているのは番地空間の分離。
- AMD-Vi の付け替えの表は装置ごとにある。だからドライバーが自分の MSI-X の表を書いても、自分に許された入口にしか届かず、核が仲立ちしなくてよい。

**作り**
- 割り込みの源は能力として渡す。
- 割り込みが来たら、知らせの語の bit を立て、待っている thread を起こす。
- ドライバーが「済んだ」と言うまで、次の割り込みは bit に溜まり、起こしを重ねない。
- level の線（ACPI の SCI など）は、済むまで IOAPIC で覆う。
- 届け先の CPU は使い手の近くにする。NVMe の待ち行列ならその CPU、入力なら窓の主体の急ぎの CPU。

**数字**：核の中は 1〜2 µs。

**1024 CPU と NUMA**：vector の表は CPU ごと（一つの CPU に約 200）、付け替えの表は装置ごと。大域の表は無い。

### 5.4 待ちと同期

**形はどこから来たか**
- ドライバーも格納庫も核の外にあるので、核の仕事は短い。だから核を横取りされない作りにでき、横取りを止める数（捨てた形）が要らない。
- 一回の核の仕事の上限は 20 µs とする。急ぎの遅れの目標 10 µs と入力の 125 µs から決めた値。
- 長い仕事（空間の取り壊し、取り消しの木、2 MiB の 0 埋め＝約 70 µs）は区切りで進み具合を物に書き、急ぎが待っていれば戻る。小さな核ではよくある形だと書いておく。

**作り**
- 核の錠は物ごとの spinlock（MCS の列の錠）。錠を持ったまま待たず、錠を持ったまま主体に何かを頼まない。
- 利用者の待ちは二つ。番地の待ち（語が期待値なら眠る、今の `wait_on_address`）と、知らせの集合（今の事象の待ち行列をこの上に作る）。番地の待ちは物理の番地で引くので、主体をまたいで働く。

**1024 CPU と NUMA**：番地の待ちの bucket は、その記憶のある node に置く。大域の錠は無い。

### 5.5 記憶（物理・空間・大きな頁・固定・NUMA・CXL）

**形はどこから来たか**
- y-cruncher は数十 GB の 2 MiB の頁を何日も固定する。4 KiB の固定の頁が 2 MiB の区画に一つでも混じると、その区画は二度と大きな頁にならない。だから区画は種類ごとに分ける（動かせる利用者の頁、固定した利用者の頁、核と DMA）。
- Zen 4 の L2 DTLB は 2 MiB の頁を 3072 項目まで持つ（約 6 GiB 届く）。1 GiB の頁は L1 DTLB にしか入らない（SOG 57647 の TLB の節）。だから 1 GiB の頁の益は測るまで決めない。
- 7600X は PCID も INVLPGB も Fixed,0。Milan（PPR 55898）には両方ある。だから TLB の撃ち落としは、二つの本物の書き方を一つの約束の後ろに置く。7600X では IPI と受け箱、INVLPGB のある機械では INVLPGB と TLBSYNC。これは継ぎ目の本物の例。

**作り**
- node ごとに頁の溜めを持ち、CPU ごとに小さな溜めを持つ。
- 口座（予約の群の記憶）は保証と上限を持ち、確保はそこへ数える。
- 合成・入力・記録の口座は保証つきなので、y-cruncher がどれだけ固定しても止まらない。固定は保証の残りからだけで、過剰に約束しない。
- 核は頁の cache も swap も持たない。足りなくなると口座の持ち主へ知らせ、持ち主が自分の cache を縮める。それでも足りなければ `N_ERR_NO_MEMORY` を返す。核は誰も殺さない。
- 核の頁は G。直写像は 1 GiB の頁で作る。
- CXL は、CPU の無い記憶の node（SRAT・SLIT・HMAT）として「遅い記憶」の段にする。群ごとの帯域は SMBE で抑えられる（PPR の CPUID 8000_0020）。
- L3 は CAT（16 の級、CPUID 0x10）と MBE を使い、画面の道の群に L3 の一部を守る。級が 16 しかないのはハードウェアの数なので、群を級に畳む。
- 直接の I/O：アプリは固定した記憶を格納庫へ渡す。格納庫はそれを NVMe の領域へ一度だけ写し、I/O ごとに IOMMU を書き換えない。

**1024 CPU と NUMA**：溜めは node ごと・CPU ごと。空間ごとの「載せた CPU」の集合は、node ごとの語の列で持つ。

### 5.6 物と権限（handle・capability）

**形はどこから来たか**：錠なしで読んで後で回収する形（捨てた形）は使わない。1024 CPU で handle を引く道は、handle の世代（今の 23 bit の場所＋8 bit の世代）と参照の数で速くできる。

**作り**
- 核の物の種類は少ない：空間、記憶（RAM・DMA・装置の窓、それぞれ型つき）、thread、予約、口座、端点、知らせ、割り込みの源、DMA の領域、doorbell の権利、主体。
- 文書・窓・接続・音は「持ち主の主体への端点」になる。利用者から見た `n_handle` はそのまま。
- 取り消しは派生の木で行う。入力の貸し、DMA の写し、走査の許しを止めるのに使う。

**数字**：handle を引くのは原子操作 2 回。毎コマの道では引かない。

**1024 CPU と NUMA**：表は主体ごと。多くの CPU が同時に握る物の参照の数は node ごとに分けて持つ。

### 5.7 やり取り（呼び出し・共有の記憶・通知）

**形はどこから来たか**：速さの規則。毎コマの道は輪、制御は呼び出し。輪の形は NVMe と xHCI の輪そのもので、この形を強いているのは装置の側。

**作り**
- (1) 呼び出し：待っている相手の thread へ、同じ CPU で直に切り替える。呼ぶ側の期限と予算を相手に貸し、使った時間は呼ぶ側に数える。使うのは制御だけ（窓を作る、文書を開く）。
- (2) 輪：共有の記憶の上の、一対一の輪。
- (3) 知らせ：輪の頭に「眠っている」の印を置く。印があるときだけ知らせ、起きている使い手には知らせない。
- 端点は小さな本文と能力を運ぶ。大きな本文は共有の記憶で渡す。今のチャンネルの意味は libc がこの上に作る。

**数字**
- 呼び出しの往復は CR3 の書き 2 回＋IBPB 1 回。値は未測で、第 0 段で測る。
- 毎コマの道の知らせは、1 画面 1 コマに 1〜2 回。

**1024 CPU と NUMA**：仕える主体は node ごとに thread を持ち、核は呼ぶ側の node の thread へ届ける。

### 5.8 主体・区画・thread と寿命

**形はどこから来たか**
- ブラウザーのせいで thread の数が多い。
- 核の仕事は短く、待つ所は核から出る点（呼び出しの返事、番地、知らせ、pager の頁違反のやり直し）に限られる。だから核の stack を CPU ごとに一つにでき、thread ごとの核の記憶は制御の塊と XSAVE の領域（AVX-512 で約 2.5 KB）だけで済む。
- thread ごとに 16 KiB の stack を持つと、10 万 thread で 1.6 GB かかる。

**作り**
- 主体の番号は thread の番号と別。区画は主体の中の空間。
- 終わりは区切りで進む取り壊しで行い、その時間は終わる主体の群に数える。
- ELF の読み込みは、核がするのは最初の束だけ。他は読み込みの主体がする。

**1024 CPU と NUMA**：thread の番号は node ごとの範囲から配る。

### 5.9 失敗と再起動

核は、落ちた主体の能力を取り消す。
- IOMMU で塞ぐ。
- 割り込みを覆う。
- BAR を外す。
- 止まったと確かめられない DMA の頁は隔離する（今の ABI のとおり）。
- 端点の相手には `N_EVENT_CLOSED` を送る。

そのあと見守りが新しいものを起こす。主体ごとの結果は次のとおり。

| 落ちた主体 | 起きること |
|---|---|
| NVMe | controller を reset し（CAP.TO まで、500 ms 単位）、格納庫が番号つきの要求を出し直す。アプリは遅れるだけ |
| 格納庫 | 書式が書込み時複写と commit なので、最後の確定へ戻る。開いた文書は `N_ERR_CLOSED`。確定前の変更（最大 5 秒分）は失う |
| 窓と合成 | 窓の登録を見守りの持つ記憶の物に置いておき、新しいものが引き継ぐ。窓は生き残り、画面は数コマ止まる |
| nvrm | GPU の reset。GPU の文脈を持つアプリには「装置を失った」が届く |
| 網 | 接続が切れる |
| 見守り・母線・ACPI | 系の再起動 |

### 5.10 記録と診断

**形はどこから来たか**：一本の記録（捨てた形）は、主体と CPU が多いと錠と順の取り合いになる。

**作り**
- 主体ごとに自分の記録の輪（記憶の物）を持ち、自分で錠なしで書く。核は CPU ごとの輪を持つ。
- 記録の主体がすべての輪を読み取り専用で写し、TSC の順に並べて serial・画面・C: へ出す。
- panic のときだけ、核が直に UART と登録された走査の面へ描く（`n_pci_screen_image` の意味を保つ）。
- 期限の記録は常に取る。急ぎの各周期について、放ち・始め・終わり・期限・CPU を、CPU ごとの輪へ数語ずつ書く。
- 合成は各コマの締め・GPU の終わり・flip・帰線を残す。
- 落ちたコマと外した期限は、予約ごとの数として task manager に出す。「カクつき 0」と言える証拠はこれだけ。

### 5.11 電源（S3）と起動

**起動**
1. Limine が、核と最初の束（見守り・記録・母線・ACPI・NVMe/AHCI・格納庫・init）を載せる。
2. 核は CPU・記憶・IOMMU を立てる。IOMMU は既定で全部を拒み、IVMD の範囲は守る。
3. 核は束の hash を確かめ、見守りに全部の能力を渡す。
4. C: はその後、格納庫の主体から見えるようになる。

**S3**
- 入り：
  1. 電源の主体が各主体に止まりを頼む（ドライバーは ACPI の主体を通して D3 へ）。
  2. 核は他の CPU を止め、CPU 0 の状態を残す。
  3. ACPI の主体が前もって渡しておいた眠りの値を、PM1 の制御へ書く。
- 戻り：
  - 戻りは BSP から始まる（ハードウェアの事実）。
  - 核は IOMMU・付け替え・LAPIC の timer を戻す。TSC は眠りで数え直しうるので、時刻の基点も直す。
  - そのあと他の CPU を一斉に起こし、主体を順に戻す。

## 8. 弱い所と未確認

- **PCID と INVLPGB が 7600X に無い。** 主体を切り替えるたびに TLB が消え、IBPB も払う。道の貸しで回数は減らせるが、残る切り替えの値段は第 0 段まで分からない。この立場が一番負けうる所。
- **格納庫の乗っ取りが装置まで届く。** NVMe の管理の待ち行列の記憶は、格納庫の I/O と同じ IOMMU の領域にある。乗っ取られた格納庫は、I/O の読みで管理の命令を書き込める（firmware の更新を含む）。格納庫はもともと全データを持つが、装置を長く壊せる点が増える。
- **GPU は核の期限の外。** 締めに間に合うかは、RM・GSP の channel の優先と、RTX 4070 の横取りの粒度で決まる。未確認。
- **TCB は核より大きい**（3 に書いたとおり）。
- **再起動は無料ではない。** 格納庫は確定前の変更を失い、nvrm は GPU の文脈を失う。
- **小さな読みが遅れる。** 4 KiB の乱読み（装置で約 50〜70 µs）は、主体の切り替えの数 µs で 5〜10% 遅れる。
- **20 µs の規律。** IOMMU の無効化の完了待ちも、区切りに載せる必要がある。
- **L3 の級は 16 しかなく、MBE の粒度は粗い。** 群が多いと、級への畳み方が効きを決める。
- **休止（S4）が重い。** 像を書く道（NVMe の主体と格納庫）を、止めた系の中で走らせる必要がある。
- **2 ソケットの EPYC は未確認。** PCID・INVLPGB・TSC の揃い・CXL の帯域の制限は、手元の資料（PPR は Milan と Raphael だけ）では確かめられない。
- **AGENTS.md との食い違い。** AGENTS.md は PCID を前提にしてよいと書くが、PPR 56713 では Fixed,0。この設計は PCID を前提にしない。
