# WebAssembly ビルド担当：反例による再考察

担当：`wasm_build`。2026-10-14。初回報告は変更せず保存した。

## 反例 1：ホストの section GC が不足シンボルを隠す

ブラウザーを `--gc-sections` 付きでリンクできても、guest TCC が同じ `libc.a` を使えるとは限らない。実際、GC を外したリンクでは、使用していない IR 関数経由の `std::__1::__next_prime` が残った。`hash.cpp` を追加して再確認すると、次に `memory.cpp` 内の `bad_weak_ptr` 基底 destructor が残った。root の ABI 修理後の独立 GC 無しリンクは exit 0 であり、未解決シンボル問題はこのリンク範囲で解消した。

したがって「ホストブラウザーがリンクできたから TCC も完成」という初期解釈は採用しない。TCC の ELF relocation、COMDAT、archive 抽出と実行は root の guest 経路で独立に確認する必要がある。単純な C アプリや TCC 本体に Wasm 全量が入ることは避けるが、Wasm を使うプログラムから必要な依存を除外する方法は使わない。

## 反例 2：容量を増やすだけでは成長失敗も参照寿命も直らない

upstream の固定 call stack capacity を巨大値へ置換すると、事前の巨大確保と現在命令位置への参照無効化を起こし得る。安定参照を持つ動的 `deque` を使い、trap の trace が必要な時だけ vector snapshot を作る方法に改めた。GC の再帰深さ閾値は残しているが、これは未処理 worklist に継続する分割点であり、参照の切捨てや実行拒否ではない。

さらに、標準 vector の例外なし OOM はプロセス abort となり、Wasm `memory.grow`/`table.grow` の失敗値と一致しなかった。Memory と Table の実格納を、算術の表現可能性と `realloc` の成否で判定する方式へ修理した。失敗前に metadata や JS の buffer を更新しない。成功後の change callback は、再配置や参照更新を次の host 呼出し前に bridge へ通知する。

ただし、モジュール解析のコンテナ、call frame、一般の C++ object と callback 自体まで、すべての OOM を JS 例外へ変換したとは主張しない。今回の修理対象は仕様が成長失敗を明示する線形メモリー・テーブルの格納である。実際の低メモリー条件の注入試験は担当範囲では未実施。

## 反例 3：中断 callback の存在と全面的な応答性は同じではない

実行時の既存命令バッチ、および解析時の section/function 境界に中断点を接続できる。これは新しいモジュールサイズ制限を導入する変更ではない。一方、単一の極端に大きい関数・巨大な一括初期化内部まで細分化したという証拠はない。実サイトの入力・再読み込み・窓操作の応答性は root の実画面・実操作で確認し、同期 C++ 処理が長ければ、その処理境界を追加で修理する必要がある。
