# ブラウザーを比べて確かめる

## なぜこうするか

- 2026-10-26：16 時間の性能の作業を、一つのサイトと固定の試験ページだけで確かめた。その間に三つの退行を入れた。見出しの字体と大きさが変わる、頁の部品が組み上がらず画像の取得が失敗する、毎コマ描く WebGL が 7 fps から 2 fps に落ちる。どれもユーザーの Hyper-V で初めて見つかった。一つのサイトは、そのサイトが通らない層を何も確かめない。
- 2026-10-16：参照と並べずに判断し、関連動画の列とチャンネル情報が欠けた画面を「正常」と言った。どう見えるべきかを決めるのは、記憶でも前の Nocturne の画面でもない。動いているブラウザーの画面が決める。
- 2026-10-26：退行を「（サイト名）の読み込み」と書いて正された。サイトを主語にすると、考えも調べる先もサイトの作りへ寄っていき、特例へつながる。壊れているのは我々のブラウザー全体。

## 三つの問い

### 開く前に：「この組は、変更が触れたすべての層を通るか。」

- 基本の組は、参照フォルダーの `TEST SITES.txt` に並ぶ全部。ユーザーが中身を変えるので、毎回読む。
- それに、変更が触れた層を通る実サイトを足す。毎コマ描く canvas・WebGL、動画の再生、検索欄への入力と送信、長いページのスクロールなど。依頼で指定されたサイトも必ず入れる。
- 一つのサイトだけで終えない。直したかったサイトが直っても、他のサイトが一つでも悪くなれば退行。
- 組に入れるのは実在のサイトだけ。自作の HTML、ローカルの試験ページ、example.com は入れない。

### 判定する前に：「参照画像のこの部品は、Nocturne の画面のどこにあるか。」

- まず参照の部品を書き出す。段組み、上部の帯、ナビゲーション、左右の欄、見出しの字体・太さ・大きさ・折り返し、本文の字体、画像・アイコン・動画の枠、ボタン、余白、固定要素、スクロールした先の内容。
- 一つずつ Nocturne の画像で探す。欠ける、形が違う、大きさが違う、位置が違う。どれか一つでもあれば失敗。
- 日々入れ替わる中身（記事、投稿、広告、おすすめ）は違いに数えない。構造、字体、大きさ、配置は違いに数える。
- 判定は、自分で画像を開いて見て行う。保存しただけ、ログに例外が無いだけ、読み込みが終わっただけでは判定にならない。

### 書く前に：「この違いは、我々のブラウザーのどの層の欠陥か。」

- 層の例：取得（HTTP/2、受け取りの勘定、Worker 経由の取得）、HTML の解析、DOM と custom element・shadow DOM、CSS のカスケード、字体の選択と読み込み、配置、描画と合成、JS の API、待ちとスケジューラー。
- 主語はブラウザーの欠陥にし、サイト名は「再現は◯◯」と添えるだけにする。
  - 例：「頁の一部の部品が組み上がらず、画像の取得が受け取りの記憶の不足で失敗する（再現は Reddit）」
  - 例：「見出しの字体と大きさが変わった（再現は YouTube の題名）」
- 同じ欠陥が組の他のサイトに出ていないかを見る。
  - 全部に出るなら、共通の層（字体、配置）。
  - ある種類の部品を使うページだけなら、その部品の層。
  - 組の広さは、層を絞る道具にもなる。
- 直すのは、仕様と共通の境界。サイト名での分岐、特定の DOM を狙った特例、UA の偽装、注入した CSS・JS で「直った」画面を作らない。
- サブエージェントへ調べものを頼むときも、依頼文の主語はブラウザーの欠陥にする。サイトの部品名を手がかりに書くと、調べる側がサイトの方へ寄っていく。

## 参照を用意する

- ユーザーの参照フォルダーは `C:\Users\cesta\OneDrive\Desktop\NOS BROWSER\WEBSITE PICS`。入っているのは次の三つ。中身と撮った日は毎回確かめる。
  - Floorp で撮った窓全体の画面（Floorp 自身の枠を含む）
  - `TEST SITES.txt`（URL の一覧）
  - 同じサイトを順に開いた性能記録（`*profile.json.gz`）
- 参照が無い、古い、または幅で段組みが変わるページでは、自分で撮る。
  - 組み込みのブラウザー（`mcp__Claude_Browser__*`）で同じ URL を開く。
  - `resize_window` で、Nocturne の頁の表示域と同じ幅・高さにしてから撮る。
  - 比べるのは同じ幅どうし。応答型のページは、幅が違えば別の段組みになる。
- 自分で撮った参照は、URL・幅と高さ・撮った日時と一緒に残す。
- 参照のブラウザーは、ログインの状態が Nocturne と違うことがある。違えばそう書く。ログインで変わる部品を判定から外すなら、その理由も書く。
- 参照のブラウザーの画面は物差しであって、Nocturne の合格の証拠ではない。

## 進め方

1. 受入表を作る。サイトごとに、URL、参照画像、照合する部品、行う操作（下へスクロールして戻る、リンク、入力）、測る値。
2. 変更前の Nocturne を撮る。
   - 基準の媒体で一台の QEMU を起動し、組の全サイトを窓・タブで開いて、まとめて撮る。
   - 起動と撮影の手順は、nocturne-project スキルの `references/qemu-visual.md`。
   - 変更前が撮れないときは、退行かどうかを判定できないと書く。
3. 変更後を同じ条件で撮る。窓の大きさ、開く順、操作をそろえる。
4. サイトごとに、参照・変更前・変更後の三枚を並べ、部品を一つずつ照合する。結果は「一致」「新しい違い（退行）」「前からの違い」のどれか。
5. 速さを同じ条件で測る（次の節）。
6. 違いを層に割り当てて、修理へ戻る。
   - 退行は、新しい機能より先に直す。
   - 直したら、もう一度組の全部を撮る。

撮った画像は `build/qa/hikaku/<日付と媒体の名>/` に、サイトと前後の分かる名で置く。基準の画像は次の回の「変更前」になるので、消さない。

## 速さを比べる

- 測るもの：
  - 毎コマ描くページは fps
  - 読み込みは、最初の本文が出るまでと、読み込みが落ち着くまでの実時間
  - 操作は、スクロールや入力の応答
  - どれも CPU の使い方も一緒に見る
- 変更前と後は、同じ媒体の条件、同じ QEMU の条件で測る。
- Floorp の性能記録は、Firefox Profiler の処理済みの形式。
  - Python の `json.load(gzip.open(...))` で読める。文字列は `shared.stringArray` に引く。
  - サイトごとの内容のプロセスは、スレッドの `eTLD+1` で分かる。一つのサイトが、画像の配信元や Service Worker の別プロセスを持つこともある。
  - CPU 時間はスレッドの `samples.threadCPUDelta`（単位は `meta.sampleUnits`）。
  - 頁の節目は、そのプロセスの GeckoMain の印 `Navigation::Start`・`DOMContentLoaded`・`Load`・`FirstContentfulPaint`・`LargestContentfulPaint`。時刻は記録の共通の時計の ms で、記録の範囲は `meta.profilingStartTime`〜`profilingEndTime`。
- 2026-10-26 の記録の百度百科は、Firefox でも読み込みに手間取った回で、普段の値ではない。基準に使うなら撮り直す。
- Floorp の測定は実機、Nocturne の測定は QEMU であることが多い。条件の違いを書いたうえで、差を倍数で書く。「普通」「他のブラウザーと同じ」とは書かない。
- 改善と呼べるのは、実時間と fps が動いたときだけ。
  - 一つのサイトが速くなっても、他のサイトが遅くなれば退行。
  - 内部の数（往復の回数、関数ごとの標本）が減っても、実時間と fps が動かなければ改善ではない。

## 書いて残す

サイトごとに、次を書く。

```text
再現の URL：
参照画像（絶対パス、撮ったブラウザー・幅・日時）：
変更前／変更後の画像（絶対パス、媒体）：
照合した部品と結果：
操作と結果：
速さ（変更前・変更後・Floorp）：
判定（一致／退行／前から）：
欠陥の層と、次に直す境界：
```

- 確かめていないものは、未確認と書く。
- Hyper-V と実機はユーザーの担当。そこでの結果を、QEMU の結果から推さない。
