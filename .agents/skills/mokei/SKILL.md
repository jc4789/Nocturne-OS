# 作業の模型

## なぜ

長い作業で筋を失うのは、判断の材料が、決める瞬間に目の前に無いから。圧縮の要約は直前の細かい作業を一番詳しく残し、ユーザーの前の言葉、自分で覆した説明、別のファイルで決まった約束を落とす。本人が書く模型も、本人の今の枠を写すので、枠と一緒にずれる。

2026-10-25 の 16 時間の会話では、ユーザーが伝えた観測（ブラウザーの worker 一本しか CPU を使わない、全体で 60〜65% を越えない）が、模型の二回目の書き換えで消えた。自分の計測で覆した説明は、書き換えで消えたまま、十四時間後に一番の説明へ戻った。本人が書き換える一枚の紙では、どちらも防げない。

だから作業場を分け、書く人を分ける。

| | 書く人 | 置き場所 | 目の前に来る時 |
|---|---|---|---|
| 模型 | 本人 | `.claude/mokei/<作業場>.md` | 圧縮・再開の後（フックが入れる）、自分で開いた時 |
| 会話の記録 | フック（事象から） | `.claude/mokei/<作業場>.jsonl` | 圧縮・再開の後 |
| コードの覚え書き | 誰でも | `.claude/oboegaki.md` | そのファイルを読む・書く時 |
| コードのつながり | codegraph（コードから） | `.codegraph/`（手元だけ、git に入らない） | 編集の直後（フックが出す）、自分で引いた時 |

置き場所は会話の始まりにフックが知らせる。デスクトップのアプリでは、再開で会話の識別子が変わっても同じ作業場が続く。フックは見せるだけで、止めない。

## 模型：今、頭に置く判断

形は自由。持つ価値があるのは次のようなもので、今の作業に要るものだけを書く。欄を埋めることは目的ではない。

- 目的：ユーザーの言葉のまま。言い換えると目的がずれる。
- 今の一番の説明（二番手があれば）、それぞれ何を見たら覆るか、何で確かめたか（その版の画面・ログ・計測、または推測）。
- 原因のありか：我々のコードから順に。なぜそこか。
- 境界の設計なら、持ち主と境界。
- 次の一手：どの説明とどの説明を分けるか。

読み返せる長さに保つ。自由に書き換えてよい。フックがすべての版を記録に残すので、消した説明も後から辿れる。済んだ作業の一覧や事実の写しは要らない。起きたことは記録と git にある。

説明を「説明」を含む見出しの下に置くと、その一行目が版の流れとして圧縮の後に並ぶ。

## 会話の記録：起きたこと

本人は書かない。フックが、ユーザーの発言（原文）、模型の版、編集したファイルを事象のたびに書き、圧縮や再開の後に、模型と一緒に次を見せる。

- ユーザーの原文（長ければ最初と最近）
- 模型の版の流れ
- 編集の流れ（時間帯ごとに多く触ったファイル）
- この会話の間のコミットと、未コミットの変更の広がり
- ユーザーの最後の発言からの時間と、圧縮の回数

要約をそのまま読むと、直前の作業へ戻りたくなる。記録は、自分の手間がどこへ行ったかを外から見せる。ユーザーの言葉と、版の流れ・編集の流れを並べて、同じ方向を向いているかを見る。向いていなければ、なぜそうなったかが今の説明の一番になる。

記録は一行一事象の JSON なので、前の版の模型やユーザーの原文は grep で探せる。「前から」「別件」と書きたくなったら、その判断がいつ、何を根拠に模型へ入ったかを版で確かめる。

## コードの覚え書き：次に触る人が知らないと困ること

コードを読んでも分からないことを苦労して知ったときに書く。会話をまたいで残り、そのファイルに触れた次の担当（サブエージェントも）へフックが出す。

- ファイルをまたぐ暗黙の約束（ある関数の返り値の単位を、別のファイルの呼ぶ側が前提にしている、など）
- 落とし穴と確かめ方（この経路は QEMU では通らない、この道具は失敗しても成功を返す、など）
- 文書の古い箇所（README や AGENTS.md の記述が今のコードと違う所）

一か所で完結する約束は、その場所の注釈に書く。覚え書きは、触れる場所と知るべきことが離れているときのもの。

一件の形（`## ` で始まる題の下に、`対象:` と `確かめた:` の行と本文）：

```
## 題
対象: kernel/src/sys/sched.c, kernel/src/sys/events.c
確かめた: 2026-10-26 67bc115e
何を、なぜ。何で確かめたか。
```

対象はリポジトリからの道（glob 可、末尾の `/` は下全部）。確かめた日とその時のコミットを書く。フックは出すときに、その後に対象へ入ったコミットと未コミットの変更を数えて添える。数があれば今のコードと照らしてから使う。違っていたら、その場で直すか消す。古い覚え書きは、無いより悪い。

## コードのつながり：どこに響くか

覚え書きは「なぜ」を持ち、どこに響くかは codegraph の索引が持つ。記号と呼出しを tree-sitter で読んだ手元の索引で、ファイルの変化を追う。設定は `codegraph.json`（third_party は外してある）。

- 編集の直後に、フックがそのファイルに頼るファイルと、編集した関数を呼ぶ所を出す。一つの区切りで一度ずつ。名前だけで推した確からしさの低いつながりは出さない。Python は名前だけのつながりが多いので出さない。
- 書く前に呼ぶ側を見たいときは自分で引く：`codegraph explore "<問いや名前>"`（原文・呼出しの道筋・影響の範囲）、`codegraph callers <関数>`、`codegraph impact <関数>`。MCP の `codegraph_explore` も同じ答えを返す。MCP のサーバーが動いている間は索引がファイルの変化を一二秒で追う。動いていない時の CLI は、先に `codegraph sync` で追い付かせる。
- 索引に出ないもの：番号で引くシステム呼出し（`common/abi.h` の `SYS_*` の表から呼ばれる）、QuickJS へ登録する表、生成した束縛、third_party。「呼ぶ所なし」は「無い」の証拠ではない。ABI の境界は自分で読む。
- 一回の explore は数万字になることがあり、文脈に残る。長い会話では、名前を挙げて問いを絞る。
- 索引はどこを読むかを決める道具で、原文の代わりではない。編集する所は今までどおり Read で読む（Edit は Read を要る）。

## 四つの問い

AGENTS.md の冒頭と同じ問い。答えが模型の中身になる。

### 書く前に：「これは誰のものか。二つ目が来たら、呼ぶ側は変わるか。」

持ち主を間違えた線は、後の修理のたびに例外と但し書きを呼ぶ。二つ目のメーカー・装置・利用者が来たと想像し、呼ぶ側に一つ目の名前が残るなら境界の位置が違う。二つ目の作者が一つ目から写すことになる部分は、共通の側に置く。一二行を正当化するのに作文が要るなら、その行があるべきかを先に考える。境界の設計は、書き始める前に模型へ数行で書き、最終報告の頭にも載せる。ユーザーはそれを読んで方向を正せる。

### 直す前に：「原因はどこにありうるか。動いている参照と我々の差は何か。」

見当が無いまま読む範囲を広げると、文脈が埋まり、圧縮が早まり、判断が消える。成熟した上流より、我々の移植・接着・渡す値に誤りがある見込みが高い。動いている参照（前に動いた回、上流の呼ぶ側、仕様書、別の実装）と我々の差を並べると、それが次の一手の候補表になる。修理の案には「原因を消すか、症状を隠すか」を問う。

### 区切りごとに：「物差しは、前の区切りより目的の方へ動いたか。」

物差しは、目的が叶ったときにユーザーが見て分かるもの（画面、操作の速さ、実機の挙動）。模型の説明が細かくなることや、内部の数が減ることとは別。区切り（ビルドと試験の一回り、コミット、圧縮、ユーザーのいない長い時間）で、ユーザーが見るものを同じ条件で見る。動いていなければ、同じ方向の次の細かい改善ではなく、なぜ効かないかを説明の一番にする。

### 言う前に：「何と何を比べて、そう言えるのか。」

「直った」「速くなった」「回帰ではない」「前から」「別件」は、同じ条件で見た二つの版を言えるときだけ。比べた二つと限界を同じ文に書く。

## 文脈の使い方

- 広く読む仕事（上流の奥、仕様書、多くのファイルにまたがる調べもの）は、問いを一つ持たせたサブエージェントに回す。返してほしいのは結論と根拠の場所。前提の監査も含め、ユーザーの許可を待たずに回してよい（2026-10-25 ユーザー確認）。
- 我々の経路上のコードは、自分の目で詳しく読む。原因が一番ありそうな場所だから。どこを読むかを我々のコードの中で探すのは、grep を重ねるより codegraph で一度引く方が早い。
- 前提の監査には、模型とコードの場所だけを渡し、自分の結論は渡さない。結論を渡すと、確かめられて返ってくるだけになる。問いは「この模型の前提のうち、コードや観測と合わないものはどれか」。

## 始まりと圧縮の後

- 会話の始まり：フックが置き場所と、この作業場の最近の模型（前の会話）を数件知らせる。続きの作業なら、その模型を先に開く。中の事実は今のリポジトリと照らす。
- 圧縮・再開の後：フックが模型と記録を入れる。要約の次の一手へ進む前に、ユーザーの原文と自分の流れを並べて読み、模型を今に合わせる。

## 終える前に

目的を一行ずつ読み返し、それぞれを何で確かめたかを書く（静的な確認・ビルド・QEMU の画面・実機はユーザー）。確かめていないものは未確認と書く。この作業で知った、次にこのコードを触る人が知らないと困ることは、覚え書きか、その場所の注釈に移す。
